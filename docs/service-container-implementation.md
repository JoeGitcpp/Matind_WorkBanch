## 0. 给实施者的总规则

### 0.1 每个会话开始前

1. 读完架构文档和本文中你负责的那一层。
2. 读「0.4 已核实的现状」里与该层相关的代码，确认它们仍是所述的样子。不一致就停下来回报，不要按本文的旧描述硬改。
3. 本文标注「实施前核实」的地方，先核实再动手，并把结论写进提交说明。

### 0.2 分支与仓库

- 三个仓库都从最新的 `origin/dev` 开新分支，不在 `uat` 上开发。
- 前端仓库本地 `uat` 上有用户未提交的改动（`apps/web/src/components/unified/filters/EngineTagManager.tsx` 等），不要暂存、提交、还原或覆盖它们。
- 一层可以跨多个仓库，每个仓库各自提交，提交说明里互相引用。

### 0.3 不可破坏的东西

| 项 | 要求 |
|----|------|
| Swift 客户端的启动契约 | `MatindCore/Sources/MatindCore/LocalServiceHost.swift` 用 `--health` 启动主机，通过环境变量 `MATIND_LOCAL_IDENTITY_STDIN`、`MATIND_LOCAL_DATA`、`MATIND_LOCAL_SERVICE_ADDR`、`MATIND_LOCAL_SERVICE_READY_FILE` 传参，并要求 `/health` 返回 `contractVersion: "local-server-v1"`、`execution: "external-sidecar"`、`loopback: true`，`/identity` 返回公钥。这些只能新增字段，不能改名或删除 |
| 现有浏览器和模型路径 | 迁移完成之前，`browser.*` 与 `model.infer` 的端到端测试必须保持通过 |
| 任务通道语义 | 签名、请求哈希、租约、执行前预留、重启后转为 `outcome_unknown` 不重做、结果重发直至确认，全部保留 |
| 设备契约红线 | 登记文档不得带工作区字段；设备归属登记账号，不可改挂 |
| 私钥 | 设备私钥不进命令行参数、环境变量、HTTP、日志 |

## 1. 契约先行

所有层开工之前，先把下列契约定成版本化的结构定义加样例，放在同一个地方，主机、后端、网页端都从这里读取。

| 契约 | 内容 |
|------|------|
| `service-manifest-v1` | 架构文档 4.1 的全部字段 |
| `service-operation-v1` | 调用、进度、取消、结果的信封；与 MCP 的 `tools/list`、`tools/call`、进度通知、取消通知的对应关系 |
| `data-handle-v1` | 字节流句柄：去向（工作区存储或留在服务器）、大小、哈希、有效期 |
| 能力编码 | `local.service.<serviceId>.<operation>` 的语法和长度上限 |
| `service-task-v1` | 任务记录，含实际执行的服务器、付款人、计量单位 |
| `metering-entry-v1` | 计量账本条目 |

要求：

- Rust 一侧放在后端仓库的共享 crate 里，沿用 `matrix_automation::local_model` 的做法（是放进 `matrix-automation` 还是新建 crate，实施前核实依赖关系后决定）。
- 每个契约附带合法与非法样例各若干，三端的测试都要跑这些样例。
- 未知字段一律拒绝，与现有契约风格一致。

验收：三端各有一个测试读取同一批样例，判定结果一致。

## 2. 第一层：主机跨平台与通用内核

### 2.1 Windows 等价实现

| 现在（类 Unix） | Windows 要求 |
|----------------|-------------|
| `flock` 防止两个主机共用一个数据目录 | 用 Windows 文件锁实现同等的独占锁；第二个实例必须启动失败 |
| 策略和身份文件要求权限位 `0600` | 文件只允许当前用户访问（检查 ACL）；创建时就设好 ACL；不满足时拒绝加载，错误码与类 Unix 一致 |
| 进程组加 `kill` 结束浏览器子进程 | 用作业对象，作业关闭时连带结束全部子进程 |
| `SIGTERM`、`SIGINT` 停止 | 响应控制台关闭事件和服务停止请求 |
| `getppid` 检测父进程是否还在 | 持有父进程句柄并等待；父进程退出后主机在 6 秒内退出 |

数据目录：

| 系统 | 默认位置 |
|------|---------|
| macOS | 不变 |
| Windows | `%LOCALAPPDATA%\Matind\local-server` |
| Linux 桌面 | `$XDG_DATA_HOME/matind/local-server` |
| Linux 系统服务 | `/var/lib/matind/local-server`，属于专用服务账号 |

设备私钥存放：macOS 维持钥匙串加标准输入传递；Windows 用当前用户的系统数据保护接口加密后落盘；无桌面 Linux 存为仅服务账号可读的文件。

### 2.2 通用内核

把 `service.rs`、`operation_store.rs`、`operation_wire.rs`、`store.rs`、`host_lock.rs` 中与具体服务无关的部分抽成内核：身份、锁、任务存储、签名与请求哈希、领取开始回传循环、策略加载。浏览器和模型改为内核之上的两个服务实现。

这一步只做结构调整，行为不变：现有测试不修改断言即可通过。

### 2.3 无桌面登记（架构文档 4.7）

- 后端新增设备码流程：申请设备码、轮询换取结果、网页端确认页。确认页显示服务器名称、操作系统、IP 归属地。
- 后端新增登记令牌：生成、设有效期和次数、撤销、列表。
- 主机新增命令：登录（设备码）、登录（令牌文件或环境变量）、状态、退出登录、安装为 systemd 服务。
- 设备码 10 分钟过期、只能用一次；轮询间隔由服务端下发，客户端遵守。

### 2.4 持续集成与打包

- `desktop-quality.yml` 增加 Windows。
- Tauri 壳产出 Windows 和 Linux 安装包；更新 `apps/desktop/README.md` 中「只面向 macOS」的表述。

### 2.5 验收

1. 三个系统上主机全部测试通过。
2. Windows 上：第二个实例启动失败；结束父进程后主机 6 秒内退出；结束主机后浏览器子进程全部消失；策略文件被其他用户可读时拒绝加载。
3. Swift 客户端在 macOS 上照常启动主机并通过身份校验。
4. 一台无桌面 Linux 用设备码登记成功，重启后以 systemd 服务自动上线。
5. 用撤销过的令牌登记失败。

## 3. 第二层：清单、执行驱动、操作协议、模型资源

### 3.1 清单与能力

- 主机加载清单时按 `service-manifest-v1` 校验，不合格的服务进入 `failed` 并给出原因码。
- 能力由清单导出，登记到后端时进入能力注册表。

### 3.2 执行驱动

| 驱动 | 要求 |
|------|------|
| 外接 | 只接受数字回环地址；禁止重定向和代理（沿用 `model_policy::validate_endpoint` 的规则）；健康检查失败时实例转 `degraded` |
| 进程 | 只运行平台签名的包，校验沿用浏览器模块的清单签名与文件哈希规则；子进程受作业对象或进程组约束 |
| 容器 | 只在 Linux 上提供；需要用户已装容器运行时；挂载显卡；不挂载宿主机敏感目录；网络默认只允许回环 |

信任分级（架构文档第 5 章）在主机里强制执行：第三方清单声明进程驱动时直接拒绝。

### 3.3 操作协议（MCP 兼容）

- 主机作为 MCP 客户端连接服务：进程驱动走标准输入输出，外接驱动走 HTTP。
- 操作对应 MCP 工具；输入输出结构取自工具声明；进度和取消用 MCP 的通知。
- 字节流不经 MCP 传递，以 `data-handle-v1` 句柄出现在输入输出里。
- 实施前核实：采用的 MCP 协议版本是否支持工具输出结构；不支持时由清单补充输出结构。

### 3.4 迁移现有两个服务

- 模型服务改写为「清单加外接驱动」，原 `local-model-v1` 路径在迁移期间并存。
- 浏览器服务改写为「清单加进程驱动」。

### 3.5 模型资源（架构文档 4.6）

- 模型库归容器管理，按内容识别格式：GGUF、safetensors、ONNX。
- 识别出 pickle 序列化（包括压缩包内含 pickle 数据的 `.pt`、`.bin`、`.ckpt`）时拒绝，提示用户换安全格式的版本。
- 下载支持魔搭与 Hugging Face，可暂停、断点续传、完成后校验哈希；官方列表里的模型哈希由平台提供。
- 硬件检测：显存、内存、磁盘；根据服务声明的需求给出「能跑、较慢、跑不了（缺什么）」三档结论。
- 外接 Ollama 时读取其已安装的模型列表供勾选，不要求填写端点和模型名。
- 配置流程的五步全部在界面上完成，界面不出现格式、路径、端点、命令。

### 3.6 验收

1. 同一个回声服务分别以三种驱动运行（容器只在 Linux），对外表现一致。
2. 任找一个现成的、走标准输入输出的 MCP 服务器，只写清单、不写适配代码即可被调用。
3. 第三方清单声明进程驱动被拒绝。
4. 导入 pickle 权重被拒绝；导入 GGUF 被识别并匹配到对话服务。
5. 本机装有 Ollama 时，用户不碰任何文件就能把其中一个模型开放给工作区。
6. 迁移后原有浏览器、模型端到端测试仍通过。

## 4. 第三层：数据通道

- 操作输入输出中的字节流一律用句柄引用。
- 去向一「落到工作区存储」：任务下发时附带限时上传地址，主机直接上传。实施前核实工作区现有的对象存储和上传机制，复用它。
- 去向二「留在服务器」：主机只发起出站连接，字节经控制面中转给调用者。要求分块、可续传（按范围请求）、校验哈希。
- 限速：每台服务器、每个工作区分别限速，数值可配置。
- 计量：中转字节数由控制面统计，写入计量账本；超出工作区每月免费额度的部分记到传输者名下。
- 授权：每次取用句柄都要过决策链，句柄本身不等于授权。

验收：

1. 一个 2 GB 文件从服务器下载到网页端，中途断网后续传成功，哈希一致。
2. 超过限速的传输被限速而不是失败。
3. 没有读取能力的成员拿到句柄也取不到内容。
4. 控制面统计的字节数与实际传输一致。

## 5. 第四层：目录、节点、权限、管理页

### 5.1 后端

- 通用服务目录取代 `local_server_model_v1`；迁移期间旧表或视图继续供现有调用方使用。
- 能力从清单注册进能力注册表，权限组对话框里按服务器、服务两级出现。
- 决策链增加蓝图授权判定器（架构文档 7.2、7.3）：
  - 批准绑定节点配置的哈希（服务器或等价组、服务、操作、固定参数）。
  - 节点配置变化后哈希不一致，批准自动失效。
  - 批准、失效、每次以蓝图身份的调用都写审计。
- 等价组（架构文档第 6 章）：入组时校验同一 `serviceId` 且所调用操作的结构一致；挑选在线且排队最短的成员；任务记录实际执行的服务器；下发后不换机器。
- 每个服务一条队列，并发上限取清单声明与所有者设置中较小者；支持取消和管理者调整顺序。
- 通用节点：实施前核实现有节点定义的唯一来源（后端 `matind-node-defs`）和蓝图调度入口，通用节点必须通过它们注册，不另建节点体系。

### 5.2 网页端

- 工作区设置里新增服务管理页；蓝图自动化板块提供入口。实施前核实工作区设置页的现有位置和组件。
- 页面内容按架构文档第 8 章：来源、谁能调、哪些蓝图能调、队列、待接收授权、试用面板、用量。
- 目录对全体成员可见；没有能力的条目显示原因和找谁开通。
- 试用面板和节点参数表单都由操作的输入结构自动生成，不为任何具体服务写专用界面。

### 5.3 验收

1. 新装一个只有清单的第三方服务，不改任何网页端和后端代码，它就出现在目录、权限组对话框、蓝图节点面板和试用面板里。
2. 没有能力的成员在目录里看得到服务，调用被拒，提示原因。
3. 以蓝图身份的节点：批准后无权成员可以通过蓝图使用；改动节点任一固定参数后，再运行被拒，提示需要重新批准。
4. 等价组中一台下线，新任务落到另一台；已下发到下线那台的任务报失败，重排时改挑在线成员。
5. 队列并发不超过上限；取消排队中的任务成功。

## 6. 第五层：计量与扣除

- 实施前核实：后端现有的点数和额度体系（AI 令牌余额、计费计量相关表），扣除必须接入现有体系，不另建余额。
- 计量账本只追加，条目按 `metering-entry-v1`。
- 付款人按架构文档第 10 章的表格确定。
- 提交时冻结，成功后结算，失败或取消全额释放。
- 结算必须按任务幂等：主机会重发同一结果直到确认，同一任务只能结算一次。
- 服务器所有者获得的点数只能用于抵扣，不提供提现入口。
- 由蓝图负责人付款的任务因额度不足被拒时，通知蓝图负责人。

验收：

1. 同一结果回执重复发送三次，只扣一次、只记一次收益。
2. 无人在场的定时蓝图从蓝图负责人扣费；负责人额度不足时任务被拒且负责人收到通知。
3. 任务失败后冻结的点数全部释放。
4. 所有者的收益可以抵扣订阅，界面上不存在提现入口。
