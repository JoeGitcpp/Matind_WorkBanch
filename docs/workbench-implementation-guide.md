# Matind Workboard 完整实现指导

日期：2026-09-23
适用仓库：`JoeGitcpp/Matind_WorkBanch`（macOS 原生 SwiftUI 客户端）
参考实现：`Matind_Frontend/apps/web`（网页端工作板）、`Matind_BackendServer/crates/matrix-server`（控制面）

本文回答三件事：现在的工作台为什么看起来是半成品；原生端应该对齐哪一套真实契约；按什么顺序、以什么验收标准把它补完整。

---

## 1. 现状诊断

### 1.1 用户看到的现象

- 登录后标签栏是空的，看不到工作板页签。
- 标签栏右侧的「+」点了没有反应。
- 工作板里的小组件看不到，也加不进去，加进去的内容刷新后可能丢失。
- 自动化蓝图只能从菜单「工具」打开，打开后只有一句「即将推出」。
- 出错时界面没有任何提示，只是空白。

### 1.2 根因

这些现象不是各自独立的小毛病，而是同一个设计缺陷的不同表现：**客户端按一套旧接口和自己想象的数据模型实现，和后端现行契约、网页端现行模型都没有对齐。**具体分四层。

**第一层：登录接口不存在。**客户端向 `/auth/v1/login` 发账号密码。这个处理函数在后端源码里有，但没有挂进路由表（`modules/auth/api/mod.rs` 没有合并它），对 matrix-server 请求会得到 404。网页端的真实做法是直接向 Supabase 用账号密码换令牌，后端只校验 Supabase 签发的令牌。之所以有时能「进去」，是钥匙串里残留了旧令牌，客户端在启动时不做任何校验就直接标记为已登录。

**第二层：工作板接口全是旧路径。**客户端调用的 `/board/list`、`/board/delete`、`/work-widget-layout/save/:boardId` 在后端路由里都不存在。现行接口是 `/api/v1/workbenches/:wb_id/boards` 这一组，而且返回结构不是 `{code,msg,data}` 包装，而是直接返回文档本体。客户端解码必然失败。

**第三层：布局模型不对。**客户端把小组件建模成 12 列网格上的坐标（列、行、宽、高），只存在本机用户默认配置里，同步请求失败也被吞掉。后端和网页端现行的工作板布局是可停靠面板文档（Dockview 序列化格式 v1），是一棵分割树加一组面板，没有网格坐标。两边根本不是同一种数据。

**第四层：界面入口是空实现，错误被吞掉。**

- 标签栏「+」的回调是空的。
- 页签右键「删除工作板」的动作也是空的。
- 自动化页是占位。
- 三个内置小组件是写死的示例 HTML，桥接里的取数和取参数调用永远不会回调，页面拿不到任何真实数据。
- 各个视图模型把错误存进了 `error` 字段，但没有任何视图去显示它。

另外还有环境因素：开发时默认连接 `http://localhost:8800`，本机没有启动后端时，工作台列表加载失败。没有工作台就没有工作板，没有工作板就没有页签，于是整条链路表现为「什么都不可见」。

### 1.3 需要清理的死代码

以下文件或类型已经不被任何地方使用，或者建立在错误模型上，应在对应阶段删除，而不是继续修补：

| 位置 | 问题 | 处理 |
|------|------|------|
| `Features/Board/Presentation/BoardTabView.swift` 中的 `BoardTabView`、`BoardTabItem`、`PluginCard` | 第二套标签栏，已无引用 | 删除，保留并迁移 `BoardContentView` |
| `Features/Workbench/Presentation/WorkbenchSidebarView.swift` | 侧边栏方案已放弃，无引用 | 删除 |
| `Features/Board/Data/BoardRepository.swift` 的旧路径实现 | 调用不存在的接口 | 按第 4 章重写 |
| `Features/Board/Data/BoardLayoutRepository.swift` 与 `WidgetInstance` 网格模型 | 模型与后端不符，本机缓存会和服务端分叉 | 按第 5 章替换 |
| `AuthState.loginWithCredentials` 调用的 `/auth/v1/login` | 后端未挂载 | 按第 3 章改为 Supabase 登录 |
| 内置插件 `com.matind.kanban`、`com.matind.showcase-card` | 写死的示例数据 | 第 6 章决定去留，不再作为「小组件」展示 |

## 2. 目标形态

### 2.1 产品边界

原生工作台是网页工作板的桌面操作界面，不是另一套独立产品。它和网页端共享同一个工作台、同一批工作板、同一份布局文档。任何一端的修改，另一端刷新后必须看到一致的结果。

据此定三条硬约束：

1. **数据只有一个权威来源：控制面。**本机只做缓存和离线只读，不做第二份可写副本。
2. **不认识的内容只读，绝不破坏。**网页端能放的组件种类远多于原生端能渲染的种类，布局文档里也可能有原生端暂不支持的结构（浮动面板、弹出窗口）。原生端遇到这些内容时必须原样保留、提示用户去网页端编辑，不能在保存时把它们丢掉。
3. **权限和并发以服务端判定为准。**创建、改名、删除、保存布局都带幂等键和期望版本号，由服务端做比较并置换；客户端不自己猜测权限。

### 2.2 分层

沿用现有的「领域 → 数据 → 表现」三层，但要补齐两件缺失的基础设施：统一的错误类型，和统一的加载状态类型。

- **领域层**只放与网络和界面无关的纯规则：工作板摘要、布局文档、组件目录、操作结果、错误分类。这一层必须能脱离应用宿主单独测试（见第 8 章）。
- **数据层**每个资源一个仓库协议，一个线上实现，一个测试替身。仓库负责路径、请求体、响应解码和错误映射，不做界面决策。
- **表现层**的视图模型只持有「加载状态 + 数据 + 可执行动作」，视图只根据状态渲染。

### 2.3 编码约束

- 任何「是否正在加载 / 是否失败 / 是否为空」都用一个枚举表达，不允许并排放几个布尔值。建议统一成「空闲、加载中、已加载、为空、失败（带错误）」五态。
- 单个函数圈复杂度不超过 10。状态路由、错误映射这类多分支逻辑拆成独立的小函数或策略表。
- 新代码用中文注释，只说明代码本身看不出来的约束。
- 标签页类型、组件种类、操作结果都用枚举，不用字符串比较散落各处。

## 3. 基础设施（阶段 P0）

这一阶段不加任何新功能，只把「能正确地连上、正确地报错」做对。后面所有阶段都依赖它。

### 3.1 登录改为 Supabase

**做法：**

- 客户端向 Supabase 的 `/auth/v1/token?grant_type=password` 提交邮箱和密码。请求头带匿名公钥 `apikey`。
- 换回的访问令牌和刷新令牌、访问令牌过期时间，一起存进钥匙串。
- 访问控制面时，用访问令牌作为 Bearer 令牌。
- 访问令牌快过期或者收到 401 时，先用刷新令牌到 `/auth/v1/token?grant_type=refresh_token` 换新。刷新失败才退出登录。

**配置：**Supabase 地址和匿名公钥对应网页端的 `NEXT_PUBLIC_SUPABASE_URL` 和 `NEXT_PUBLIC_SUPABASE_ANON_KEY`。原生端放进构建配置文件，区分开发和发布两套，不写死在源码里。

**当前用户：**登录成功后，调用控制面的当前用户接口，取得雪花用户编号和展示名。这个编号就是本机服务器所有者编号的来源。

**启动流程：**

- 启动时如果钥匙串里有令牌，先进入「正在恢复登录」状态。
- 校验通过或者刷新成功后，才进入主界面；否则回到登录页，并说明原因。
- 不再像现在这样，看到令牌存在就直接标记为已登录。
- 读钥匙串放在窗口出现之后执行（已修复）。

**验收：**

- 没有令牌时，停在登录页。
- 令牌过期时，能自动刷新。
- 刷新令牌也失效时，回到登录页并提示「登录已过期」。
- 控制面没有启动时，提示「无法连接服务器」，而不是空白主界面。

### 3.2 网络层扩展

现有网络客户端只支持 GET 和 POST，只会解码 `{code,msg,data}` 包装。后端现在有两类响应，必须显式区分：

| 响应族 | 典型接口 | 形状 |
|--------|----------|------|
| 旧包装族 | 工作台列表、通知、组件目录 | `{code, msg, data, timestamp}` |
| 文档族 | 工作板增删改查、面板布局 | 直接返回文档；失败时返回工作板错误体 |

要求如下：

- **请求方法：**支持 GET、POST、PUT、PATCH、DELETE。DELETE 要能带请求体，因为删除工作板需要传期望名称和期望版本。
- **请求编号：**每个请求生成一个 `x-request-id`。响应里的 `x-request-id`、`x-operation-id`、`Retry-After` 读出来，交给上层。
- **成功解码：**解码方式由调用方指定：按包装族解码，或按文档族解码。不要靠猜。
- **失败解码：**
  - 文档族失败时，解码工作板错误体。字段有错误码、说明、请求编号、字段错误、前置条件名、当前版本号、建议重试秒数、是否可重试。
  - 包装族失败时，读 `code` 和 `msg`。
- **错误类型：**统一映射为一个领域错误枚举，至少分这几类：
  - 未登录
  - 无权限
  - 不存在
  - 校验失败（带字段错误）
  - 版本冲突（带前置条件名和当前版本）
  - 处理中（带操作编号）
  - 服务暂不可用（带重试建议）
  - 网络不可达
  - 解码失败

  视图只认这个枚举，不去解析字符串。

### 3.3 错误和状态必须可见

每个视图模型对外暴露一个加载状态枚举，每个视图都要处理全部五种状态。失败状态显示错误说明，并给出「重试」按钮。空状态给出下一步动作，例如「新建第一个页面」。

**验收：**

- 断开后端时，工作台选择器显示「无法连接服务器」和重试。
- 后端恢复后，点重试能正常加载。

## 4. 工作台与页签（阶段 P1）

### 4.1 工作台列表

**接口：**`GET /api/v1/workbenches`，包装族。

**返回字段（驼峰命名）：**

- 编号 `id`，是 64 位整数
- 名称 `name`、描述 `description`、图标 `icon`
- 所有者编号 `ownerId`，以及当前用户是否是所有者 `isOwner`
- 所属工作区编号 `workspaceId` 和名称 `workspaceName`
- 当前用户的角色 `role`
- 成员数 `memberCount`
- 创建时间 `createTime`、更新时间 `updateTime`

工作台编号就是后续所有工作板接口路径里的 `:wb_id`。

**行为：**

- 恢复上次选中的工作台。上次的工作台已经不在列表里时，选第一个。
- 列表为空时，显示「还没有可用的工作台」，并提供「在网页中打开工作区设置」。

### 4.2 页签模型

标签栏是唯一的导航入口，页签类型用枚举表达：

- **工作板页签**：对应一个服务端工作板。
- **自动化页签**：可以是自动化总览，也可以是某个工作板绑定的蓝图。
- **设置页签**：设置。
- **主页页签**：网页端固定存在的「主页」，对应 Agent 主页表面，使用另一套 24 列布局契约。这一项放到后续阶段，P1 不做。

**关闭和删除是两回事。**点页签上的叉，只是在本次会话里把页签收起来，工作板仍然存在，可以从「所有页面」菜单重新打开。删除是危险操作，只能从工作板的「管理」菜单进入。当前实现把「关闭标签」和「删除工作板」并排放在同一个右键菜单里，容易误删，需要拆开。

标签栏始终可见。没有选中工作台时，「+」禁用，悬停提示原因。工作板目录正在加载或者加载失败时，「+」也禁用，并分别提示「加载中」或「加载失败」。

### 4.3 工作板目录

**接口：**`GET /api/v1/workbenches/:wb_id/boards`，文档族。

**返回：**

- 结构版本 `schemaVersion`，固定为 `"1"`
- 工作区编号 `workspaceId`
- 工作板摘要数组 `boards`

**每个摘要的字段：**

- 编号 `id`、名称 `name`
- 布局版本号 `layoutVersion`、访问版本号 `accessRevision`
- 权威来源类型 `authorityKind`、权威凭据编号 `authorityReceiptId`
- 内容能力 `contentCapability`，取值为无、只读、填写、编辑
- 设置能力 `settingsCapability`，取值为无、管理

**能力决定界面：**

- 内容能力不是「编辑」时，布局只读：不能加组件，不能拖拽。
- 设置能力不是「管理」时，改名和删除不可用。

界面按能力隐藏或禁用入口，但最终仍以服务端的判定为准。

### 4.4 新建工作板

**交互：**和网页端一致，不弹对话框。点「+」直接创建，名称取「新页面 N」，N 取当前已有「新页面」序号的最大值加一。创建成功后切到新页签，失败时在标签栏附近提示原因，并允许重试。

**接口：**`POST /api/v1/workbenches/:wb_id/boards`。

**请求体：**

- 结构版本 `schemaVersion`，固定为 `"1"`
- 名称 `name`
- 幂等键 `idempotencyKey`，一个新的 UUID

名称要去掉首尾空白，长度不超过 255。后端拒绝未知字段，请求体里不能多带任何字段。

**成功响应：**

- 结构版本
- 结果 `outcome`：已确认 `confirmed`，或者凭据对账完成 `receipt_reconciled`
- 操作编号 `operationId`
- 新工作板摘要 `board`

同一次点击因为网络原因重试时，必须复用同一个幂等键，避免建出两块板。

### 4.5 改名

**交互：**入口在工作板「管理」菜单里，打开设置对话框修改名称。也可以双击页签，直接在页签上改名。

**接口：**`PATCH /api/v1/workbenches/:wb_id/boards/:board_id`。

**请求体：**结构版本、名称、幂等键。

### 4.6 删除

**交互：**入口在工作板「管理」菜单的危险区。用户必须输入完整的工作板名称才能确认，也可以填写删除原因。删除成功后，切回第一个页签。

**接口：**`DELETE /api/v1/workbenches/:wb_id/boards/:board_id`，带请求体。

**请求体：**

- 结构版本
- 期望名称 `expectedName`
- 期望访问版本号 `expectedAccessRevision`：取目录里摘要的 `accessRevision`，按十进制字符串传
- 幂等键
- 原因 `reason`（可选）

**失败处理：**

- 返回 412 且前置条件是访问版本时，说明别处改过这块板。刷新目录，并提示用户重新确认。
- 返回 503 且结果为「处理中」时，按操作编号稍后查询结果，界面显示「正在删除」。

### 4.7 暂不做的

- 拖拽排序：后端有排序接口，但网页端没有入口。原生端先不做，避免两端排序行为不一致。
- 复制工作板：它还返回旧的大对象，暂不做。

**P1 验收：**

- 在原生端新建、改名、删除工作板，网页端刷新后结果一致；反之亦然。
- 断网时新建会失败，恢复网络后重试不会产生两块板。
- 没有管理能力的成员看不到删除入口；直接调用接口也会被拒绝，并显示「无权限」。
- 关闭页签后重启应用，工作板还在。

## 5. 面板布局（阶段 P2）

这是整个工作台最关键、也最容易做坏的部分。

### 5.1 契约

**接口：**`GET` 和 `PUT /api/v1/workbenches/:wb_id/boards/:board_id/panel-layout`，文档族。布局按工作板存储，不按用户存储；读和写都要求编辑权限。

**读取返回：**

- 结构版本
- 工作区编号 `workspaceId`、工作板编号 `boardId`
- 布局文档 `layout`
- 布局版本号 `layoutVersion`

**保存请求体：**

- 结构版本
- 布局文档 `layout`
- 期望布局版本号 `expectedLayoutVersion`
- 幂等键

**保存响应：**读取返回的全部字段，再加一个「是否为重放」`replayed`。

**冲突：**返回 409，前置条件为布局版本。

**限制：**文档不超过 1 MiB，嵌套深度不超过 64，面板不超过 512 个。

旧的 `/boards/:board_id/layout` 已经退役，调用会返回 503 和退役错误码，不要再用。个人主页布局是另一套接口 `/api/v1/board-layout`，和这里无关。

### 5.2 布局文档结构

布局文档是 Dockview 序列化格式 v1，由网页端的共享协议定义（`packages/protocol/src/dockview-layout.ts`）。顶层包括以下部分：

- **分割树 `grid`**：
  - 根节点是一个分支，带方向（水平或垂直）和整体宽高。
  - 分支里包含子分支或叶子。
  - 每个叶子是一个面板组，记录组内有哪些面板，以及当前显示哪一个。
- **面板表 `panels`**：以面板编号为键。每个面板记录：
  - 组件种类 `contentComponent`
  - 标题 `title`
  - 组件参数 `params`
  - 可选的最小和最大宽高
- **可选结构**：当前激活组、浮动组 `floatingGroups`、弹出组 `popoutGroups`。

空布局是一个没有子节点的水平根分支，加一个空的面板表。

### 5.3 原生端的渲染策略

原生端不能直接运行 Dockview，需要自己实现一个 Dockview v1 子集的原生渲染器：

- **分支**渲染为可拖动分隔条的水平或垂直分栏。子节点的尺寸比例取文档里记录的大小。
- **叶子**渲染为一个面板组。组里有多个面板时，显示组内小页签，只渲染当前激活的面板。
- **面板**交给第 6 章的组件渲染器注册表处理。

### 5.4 保留未知结构

布局文档在内存里要以两种形态并存：

- **原始文档**：完整的 JSON 树，不丢任何字段。
- **结构化视图**：从原始文档里解析出原生端认识的那部分。

所有编辑操作都表达为对原始文档的定点修改：

- 新增面板
- 移除面板
- 调整分隔比例
- 在组内切换当前面板
- 修改面板参数

保存时提交修改后的原始文档，不从结构化视图重新序列化。这样网页端写入的、原生端不认识的字段就能完整保留。

文档里有浮动组、弹出组，或者原生端无法解析的节点时，这块工作板进入「只读」模式：原生端可以查看它认识的部分，界面提示「此页面包含桌面端暂不支持的布局，请在网页中编辑」，并提供「在网页中打开」。只读模式下不产生任何保存请求。

### 5.5 保存与冲突

**保存节奏：**编辑后防抖 800 毫秒再保存，和网页端一致。同一时刻最多只有一个保存请求在途。新的修改在在途请求返回后合并提交，期望版本号取最新成功保存的版本。

**冲突处理（409）：**暂停自动保存，提示用户「页面已在别处修改」，提供两个选择：

- **载入远端**：丢弃本地未保存的修改，重新读取布局。
- **以本地覆盖**：用远端的当前版本号作为期望版本号，重新提交本地文档。

**本机缓存：**只作为离线只读的最近一次快照，按工作台编号和工作板编号分键，同时记录布局版本号。离线时显示缓存内容，并标注「离线，只读」，不允许编辑。现有「本机缓存优先、同步失败静默」的做法必须去掉。

**P2 验收：**

- 网页端建好的多分栏、多组、组内多页签布局，在原生端能按原比例显示。
- 在原生端调整分隔比例后，网页端刷新能看到。
- 网页端放了原生端不认识的组件时，原生端改了别的面板再保存，这个未知组件在网页端依然完好。
- 含浮动面板的工作板在原生端只读，不会发出任何保存请求。
- 两端同时修改时，后保存的一方收到冲突提示，数据不会被静默覆盖。

## 6. 小组件（阶段 P3）

### 6.1 种类以网页端为准

面板的组件种类字段 `contentComponent`，取值是网页端组件注册表里的种类名。网页端当前约有 37 种，例如：

- 超级表格 `HyperTable`、图表 `Chart`
- 文件管理 `FileManager`、AI 对话 `AIConversation`
- 代码框 `CodeBox`、界面视图 `UIView`
- 以 `ui.` 开头的一组基础组件

定义在 `apps/web/src/core/widgets/setup.ts`。

原生端不能另起一套种类名。现有内置插件的编号（例如 `com.matind.chart`）和网页端的种类名不在同一个命名空间里，放进布局文档会让网页端无法识别。

### 6.2 渲染器注册表

原生端维护一张渲染器注册表：键是组件种类名，值是渲染方式。渲染方式分三类，用枚举表达：

- **原生渲染**：用 SwiftUI 实现。优先覆盖高频、适合原生体验的种类，例如文本、图表、表格只读视图。
- **网页渲染**：用 WKWebView 承载一个页面。适用于网页端已有实现、原生重写成本高的种类。页面来源优先选网页端提供的单组件嵌入路由；没有的话，先归为下面的「暂不支持」。
- **暂不支持**：显示占位卡片，写明组件名称和「在网页中查看」。它在布局里的位置、尺寸、参数都原样保留。

### 6.3 组件目录

- 「添加组件」弹窗列出的是网页端注册表和原生渲染器注册表的交集，也就是原生端确实能渲染的种类。
- 已经在布局里、但原生端不支持的种类，不出现在添加列表里，只作为占位显示。
- 目录数据的权威来源需要和网页端统一。建议把网页端注册表导出成一份共享的组件目录清单，内容包括种类名、显示名、分类、默认尺寸、参数结构，放进 `packages/protocol`，两端都从这份清单生成。
- 在这份清单出来之前，原生端先手工维护一份，只包含它支持的种类，并用测试锁定这些种类名和网页端一致。
- 后端的 `/widget/available`、`/marketplace/*` 接口是否要作为目录来源，目前没有定论，见第 10 章。

**添加流程：**在当前激活的面板组里新增一个面板。面板编号用新的 UUID，种类取所选组件，标题取组件显示名，参数取组件默认参数。然后按第 5 章的方式保存。

### 6.4 插件桥接

现有桥接的调用永远不回调，必须重做，或者限定范围。

- 每个请求都带请求编号，宿主处理完后，按编号回调网页页面。这样页面里的调用才能真正拿到结果或错误。
- 数据请求不能透传任意路径。只允许调用插件清单里声明过的接口前缀；访问令牌不交给网页页面，由宿主代发请求。
- 读取组件参数，返回的是该面板在布局文档里的参数。修改参数时，走第 5 章的定点修改和保存流程。
- 页面只能加载应用包内的本地文件，禁止跳转到外部地址。现有的「允许文件地址互相访问」这个开关要评估后收紧。

### 6.5 内置示例插件的去留

看板和展示卡片这两个示例插件是写死的数据，不对应网页端的任何种类，从组件目录里移除。

图表插件如果要保留，必须改造成网页端 `Chart` 种类的一个网页渲染器：读取面板参数，通过宿主取数。否则一起移除。

**P3 验收：**

- 在原生端添加一个图表组件，网页端刷新后能看到同一个图表，参数一致。
- 网页端添加一个原生端不支持的组件，原生端显示占位卡片；原生端保存别的修改后，网页端这个组件不受影响。
- 插件页面发出的数据请求能拿到结果；请求清单里没有声明的接口会被拒绝。

## 7. 自动化蓝图（阶段 P4）

### 7.1 边界

蓝图的图形编辑器留在网页端，原生端不重写。原生端负责四件事：

- 看到这块工作板绑定了哪个蓝图
- 手动触发运行
- 实时看到运行过程和结果
- 需要编辑时，跳转到网页编辑器

### 7.2 契约

**工作板绑定的蓝图：**

- 查询：`GET /api/v1/ai/blueprints?hostKind=board&hostId=<工作板编号>`
- 一块工作板最多绑定一个蓝图。
- 返回字段包括：编号、名称、描述、图、版本、宿主类型、宿主编号、是否官方、是否启用。

**触发运行：**`POST /api/v1/automation/bindings/:binding_id/runs`

- 请求带界面编号 `surfaceId`
- 幂等键
- 原因 `reason`，取值为手动 `manual`

**运行事件：**`/api/v1/automation/bindings/:binding_id/runs/:dispatch_id/events`

- 服务端事件流。
- 断线后约 1.5 秒重连，并从最后一个事件继续。

**已经退役、不要用的旧接口：**

- `/api/v1/blueprints/:id/runs`：返回 410。
- 工作板的 `/blueprint-binding`：返回 503 退役。

**打开网页编辑器：**`/<语言>/app/blueprint-editor?hostKind=board&hostId=<工作板编号>&hostTitle=<工作板名称>`

**待确认：**`/api/v1/workbenches/:workbench_id/blueprints` 这一组接口里，路径参数是 UUID 类型；工作板接口里，工作台编号是 64 位整数。两者能不能共用同一个编号，还没有确认。原生端第一版只用上面按宿主查询的接口。绑定对象的完整字段，以共享协议 `packages/protocol/src/automation-bindings.ts` 为准。

### 7.3 界面

- 每块工作板的工具栏上加「自动化」入口，打开这块工作板的自动化页签。
  - 没有绑定时，显示「这个页面还没有自动化」，并提供「在网页中创建」。
  - 有绑定时，显示蓝图名称、启用状态、最近几次运行，以及「立即运行」按钮。
- 运行中，显示实时事件列表和当前状态。完成后显示结果摘要，失败时显示失败的节点和原因。
- 菜单里的「自动化蓝图」改为总览：列出当前工作台下所有工作板的绑定和最近运行状态，不再是占位页。

### 7.4 和本机服务器的关系

蓝图的执行位置由服务端判定。原生端不能因为自己是桌面程序，就在界面进程里执行蓝图。

需要本机执行的蓝图，走本机私有服务器的执行契约：目标为本机 `local`，语义为本机私有服务器 v1 `local-private-server-v1`。它依赖本机服务器已登记、已授权给这个工作区，并且持有有效的短授权，见《本机私有服务器执行方向》文档。旧契约 v1 里的「客户端执行」不等于本机私有服务器，两者不能混用。

**P4 验收：**

- 在网页端给工作板绑定蓝图后，原生端能看到这个绑定。
- 在原生端点「立即运行」，能看到实时事件和最终结果；网页端的运行记录里有同一次运行。
- 断网再恢复后，事件流能续上，不会重复触发运行。

## 8. 测试与工程

### 8.1 测试宿主问题

现在的单元测试挂在沙盒应用上运行。测试宿主在系统沙盒初始化阶段卡住，测试一个都没跑起来。这是结构问题，不应该靠临时改构建参数绕过。

**解决办法：**

- 把领域层和数据层抽成一个本地 Swift 包，例如 `MatindCore`。它不依赖 AppKit，也不需要沙盒。
- 这些逻辑的测试放进包里，用 `swift test` 直接跑，不需要应用宿主。
- 应用目标只保留表现层，依赖这个包。
- 需要宿主的界面测试单独成一个目标，用于端到端流程。

### 8.2 每阶段必须有的测试

- **网络层**：两类响应族的解码；工作板错误体到领域错误枚举的映射；请求编号和幂等键的传递；DELETE 带请求体。
- **工作板**：新建时序号的计算；重试时幂等键复用；删除时带上期望版本；412 和 503「处理中」的处理。
- **布局**：
  - 空布局能解析
  - 多层分割树能解析
  - 保存时原样保留未知字段
  - 含浮动组时进入只读
  - 超出限制时拒绝
  - 409 冲突时的两种处理
  - 防抖和在途合并
- **组件**：注册表的交集计算；种类名和网页端一致；不支持的种类显示占位。
- **蓝图**：按宿主查询；运行的幂等；事件流断线重连不重复触发。

用网页端或后端测试里的真实响应做夹具，不手写臆测的结构。

### 8.3 本地开发环境

1. 启动控制面：在 `Matind_BackendServer` 里运行 `cargo run --bin matrix-server`，确认 8800 端口能访问。
2. 配置 Supabase 地址和匿名公钥，与网页端开发环境使用同一个 Supabase 项目。
3. 网页端同时跑起来（`Matind_Frontend` 里的 `pnpm dev`），用来做两端一致性的对照验证。
4. 构建原生端：用 `xcodegen generate` 生成工程，然后用 Xcode 或 `xcodebuild` 构建运行。

## 10. 待决事项

以下几项需要产品或控制面给出结论，在对应阶段开始前确定：

1. **组件目录的权威来源。**是在 `packages/protocol` 导出共享清单，还是以后端 `/widget/available` 或组件市场接口为准。建议前者。后端这两组接口目前与面板布局没有衔接。
2. **网页组件的嵌入路由。**网页端能否提供「只渲染单个组件」的嵌入页面，供原生端的网页渲染器使用。如果不能，原生端能支持的种类只能靠原生重写，P3 的覆盖面会明显变小。
3. **原生端首批原生渲染的种类。**建议从文本、图表、超级表格只读视图开始。
4. **蓝图接口的工作台编号类型。**UUID 和 64 位整数的不一致，需要控制面澄清。
5. **通知模块。**现有通知接口在后端已标注废弃：未读数接口的 `data` 是整数，全部已读应该调用 `/notification/readAll`。客户端当前的解码和请求体都不匹配。是先修旧接口，还是直接迁到自动化收件箱接口，需要确定。
6. **主页表面是否纳入原生端**，以及纳入的时间点。
