# 服务容器架构设计

日期：2026-10-13
状态：草案，待确认
前置文档：`local-service-platform-prd.md`（第二版）。本文在它之上调整，冲突之处以本文为准，变更对照见第 15 章。
涉及仓库：`Matind_WorkBanch`（Swift 客户端）、`MatrixFactoryFrontend`（网页端、Tauri 壳、执行主机）、`MatindBackend_Rust`（控制面）

---

## 1. 一句话

客户端启用服务后，这台机器就是一台服务器。服务器是一个通用容器，可以安装官方或第三方服务；服务以节点的形式出现在工作区里，工作区成员和蓝图在被指定的权限之下调用。容器不关心服务具体做什么。

## 2. 系统组成

| 部分 | 职责 |
|------|------|
| 网页端 | 轻量，任何地方都能打开。拥有全部功能，权限之内可以访问一切，包括管理服务器和服务 |
| 客户端 | 两个职责：一是本地工作台，让特定面板和 3D 小组件更稳更快；二是服务器容器，启用服务后把本机注册为服务器 |
| 控制面 | 身份、授权、任务调度、数据中转、计量 |

客户端在各平台的职责：

| 平台 | 本地工作台 | 服务器容器 |
|------|-----------|-----------|
| macOS | 有（现有 Swift 客户端） | 有 |
| Windows | 有 | 有 |
| Linux | 暂无 | 有，可以无桌面运行 |

真正执行服务的是执行主机 `matind-local-service`（Rust）。它已经存在，位于 `MatrixFactoryFrontend/apps/desktop/local-server`，由 Swift 客户端和 Tauri 壳共用。界面只负责启停主机、编辑所有者策略、显示状态。

界面的分工：macOS 保留现有 Swift 客户端；Windows 和 Linux 使用现有 Tauri 壳（`MatrixFactoryFrontend/apps/desktop/src-tauri`）。Linux 上的壳只提供服务器管理界面。

## 3. 核心概念

### 3.1 服务器

一台启用了服务的客户端。

- 归属登录客户端的账号，沿用现有契约 `local-server-v1`，不改归属规则。
- 个人的机器和团队的机器没有区别，都是同一种东西。
- 一个工作区可以有多台服务器；一台服务器可以授权给多个工作区。
- 状态与在线是两个独立维度，沿用第二版 4.1。

### 3.2 服务

装在服务器上的一个功能单元，由一份清单描述。容器只认清单，不认具体服务。

### 3.3 操作

服务对外提供的一个可调用动作，带输入结构和输出结构。读一个文件、写一个文件、跑一次推理、生成一张图，都是操作。

### 3.4 能力

对一个操作的使用许可，编码为 `local.service.<serviceId>.<operation>`，由清单导出。

能力是唯一的权限概念。访问、读取、写入、修改、删除、调用，在架构上没有区别，都是「某个主体能不能用某个操作」。第二版里的调用类、数据类、管理类只作为界面上的分组标签保留，不参与判定逻辑。

### 3.5 节点

蓝图里只有一种「服务调用」节点，由（服务器、服务、操作）三者确定。端口和参数表单从操作的输入输出结构自动生成。新增服务不需要写新节点。

### 3.6 任务

每一次操作调用是一个任务，状态机沿用第二版 7.1。

## 4. 通用容器

### 4.1 服务清单

| 字段 | 内容 |
|------|------|
| 标识与版本 | 反向域名风格的 `serviceId`，语义化版本 |
| 来源 | 官方或第三方，见第 5 章 |
| 运行方式 | 使用哪种执行驱动及其参数 |
| 操作列表 | 每个操作的名称、输入结构、输出结构、是否长任务、是否产生或消费字节流 |
| 资源需求 | 磁盘、内存、是否需要显卡、并发上限 |
| 配置项 | 类型化字段，界面据此生成表单 |
| 健康检查 | 检查方式和间隔 |
| 计量单位 | 每个操作按什么计量 |

### 4.2 执行驱动

容器「怎么跑一个服务」只有三种方式：

| 驱动 | 含义 | 平台 |
|------|------|------|
| 外接 | 连到用户已经运行的本机回环端口 | 全平台 |
| 进程 | 主机启动并监管一个子进程 | 全平台 |
| 容器 | 主机启动一个容器并挂载显卡 | 先支持 Linux |

### 4.3 操作协议

主机和服务之间只有一套调用方式：列出操作、调用、进度、取消、结果。

操作层与 MCP 兼容：自带 MCP 服务的项目不写适配器即可接入。身份、授权、字节流、计量不在 MCP 范围内，由容器外层负责。

操作流程复杂的服务（先提交、再轮询、再取结果）用一个小的适配程序包起来，适配程序本身是一个进程型服务。

### 4.4 两条通道

容器从第一版起就具备两条通道，所有服务共用，没有哪个服务需要专门的通道。

| 通道 | 承载 | 现状 |
|------|------|------|
| 任务通道 | 小的结构化数据：操作输入、输出、状态 | 已有，签名的领取、开始、回传三步协议，结果上限 64 KiB |
| 数据通道 | 字节流：文件、图片、视频、流式文本，双向 | 没有，需要新建 |

数据通道有两个去向，由操作在清单里声明：

- 落到工作区存储：主机凭任务附带的限时地址直接上传，控制面不经手字节。
- 留在服务器上：字节经控制面中转给调用者，限速并计量。

操作的输入输出里用句柄引用字节流，不把字节塞进任务通道。

经控制面中转的流量按三步演进，中转始终保留作为后备：

| 阶段 | 做法 |
|------|------|
| 首版 | 全部经控制面中转。每台服务器、每个工作区分别限速；每个工作区每月有一笔免费中转流量，超出部分从传输者的个人额度扣点数 |
| 第二步 | 桌面客户端与服务器在同一局域网内时直接连接，不经控制面 |
| 第三步 | 跨网络直连（打洞）。国内大量宽带处于运营商级 NAT 之后，成功率有限，失败时回落到中转 |

限速值和每月免费流量按平台实际带宽成本另行确定。

### 4.5 不随抽象改变的安全边界

- 云端只能调用清单里声明过的操作，输入先过结构校验。云端不能下发代码或命令。
- 主机每次执行前核对所有者的本机策略和云端授权，两者都通过才执行。
- 本机不开入站端口。
- 任务通道的签名、租约、不重复执行语义保留。

### 4.6 模型资源

面向没有编程基础的用户。配置任何模型都和配置大模型一样简单，界面上不出现格式、路径、端点、命令。

模型是容器管理的资源，不属于某个服务：

- 服务在清单里声明自己需要哪一类模型（例如对话模型、结构化决策模型、生图模型）。
- 同一份权重可以被多个服务使用。
- 运行 LAYA 的是一个官方服务，它声明需要「结构化决策模型」；用户只需要在下面的流程里选好权重。

配置流程，全部是图形界面：

1. 选模型：从官方模型列表里选；或者「导入」，选择本机的文件或文件夹，或者粘贴模型页面的链接（魔搭、Hugging Face）。
2. 检查能不能跑：容器检测显存、内存、磁盘，告诉用户能不能跑、大概多快。跑不了时写明差什么，并推荐更小的版本。
3. 下载：显示进度，可以暂停，支持断点续传，完成后自动校验。
4. 试一下：用自动生成的试用面板跑一次。
5. 开放：选择开放给哪些工作区，复用第 7 章的授权。

规则：

- 格式自动识别：容器按文件内容判断格式，并匹配能运行它的服务。用户不选格式。
- 只接受安全格式：safetensors、GGUF、ONNX。拒绝 pickle 序列化的权重（常见于 `.pt`、`.bin`、`.ckpt`），因为加载这类文件时可以执行任意代码。官方列表里的模型由平台给出哈希。
- 国内下载默认走魔搭，Hugging Face 在大陆访问不稳定。
- 已经在用 Ollama 这类工具的用户：走外接驱动，模型仍由该工具管理；容器读取它已安装的模型列表，用户勾选即可，不需要填端点和模型名。这取代现在手工编辑 `model-policy.json` 的方式。

### 4.7 服务器登记

有桌面的机器在客户端里用现有的浏览器登录完成登记。无桌面的机器用命令行，采用主流命令行工具的两种做法。下文命令名 `matind-server` 只是示意，正式名称待定。

设备码登录（OAuth 2.0 设备授权流程，RFC 8628，与 `gh auth login`、`az login --use-device-code` 同类）：

1. 在服务器上运行 `matind-server login`。终端显示一个链接、一个 8 位代码和一个终端二维码。
2. 用户在手机或任意电脑上打开链接，登录 Matind，输入或核对代码。
3. 确认页显示这台服务器的名称、操作系统、IP 归属地，并提示「只确认你自己正在操作的服务器」。
4. 用户确认后，命令行自动收到结果，在本机生成设备密钥并完成登记。服务器归属确认的账号。

约束：代码 10 分钟有效，只能用一次；设备私钥只在本机生成，不经过网络。

登记令牌（与 Tailscale 认证密钥、GitHub Actions 运行器登记令牌同类），用于批量部署和自动化：

- 用户在网页端生成登记令牌，可以设置有效期和可用次数，可以随时撤销。
- 服务器上运行 `matind-server login --token-file <文件>`，或通过环境变量传入。令牌不放在命令行参数里，因为进程列表对同机其他用户可见。
- 服务器归属生成令牌的账号。

命令行只保留少量命令：登录、状态、退出登录，以及安装为系统服务（Linux 上是 systemd 服务）。服务和模型的管理在网页端的服务管理页完成。

## 5. 服务来源与信任分级

| 来源 | 谁提供清单 | 可用驱动 | 界面标示 |
|------|-----------|---------|---------|
| 官方 | 平台签名发布 | 全部 | 官方 |
| 第三方 | 服务器所有者自备 | 外接、容器 | 未验证 |

进程驱动以主机的权限运行代码，因此只接受平台签名的包。第三方服务在所有者自己的机器上运行，风险由所有者承担；调用方的风险是数据会被这台机器看到，这一点由工作区的邀请制信任覆盖。

## 6. 多服务器

- 工作区服务目录按服务器分组，一台服务器下列出它的服务和操作。
- 同一服务可以来自多台服务器，节点上有「来源服务器」参数。
- 指定来源：节点选定某一台服务器。来源离线时报错，不自动切换，沿用第二版 8.2。
- 等价组：工作区管理员可以把几台服务器上的同一服务标为等价。节点的来源选择「任意可用」时，控制面在组内挑一台在线且排队最短的。

等价组的约束：

- 组内成员必须是同一个 `serviceId`，且节点调用的操作在每个成员上都存在、输入输出结构一致。不满足的成员不能入组。
- 等价是管理员的声明，平台不验证各台机器的结果是否相同（例如模型版本不同）。管理页上列出组内各成员的服务版本，供管理员判断。
- 任务一旦下发到某台服务器，就不再换到另一台。这台服务器掉线时任务按第二版 7.2 报失败；重排时重新在组内挑选。
- 每个任务记录实际执行的服务器，用于审计和计量。
- 调用者需要对被挑中的那台服务器上的操作持有能力。管理页提供按等价组一次分配能力的入口。

## 7. 权限与授权

### 7.1 授权链

所有者把服务授权给自己所在的工作区，工作区接收后在内部分配。只能收窄，不能扩大。沿用第二版第 5 章。

### 7.2 决策链

沿用第二版 5.2 的判定器链，在成员层增加一个判定器。成员层任一允许即可：

| 判定器 | 允许的条件 |
|--------|-----------|
| 成员组 | 调用者所在的权限组持有该能力 |
| 提供者席位 | 调用者是该服务器的所有者或管理者 |
| 蓝图授权（新增） | 本次调用来自一个被批准以蓝图身份调用该操作的节点 |

### 7.3 蓝图作为授权对象

蓝图里的每个服务节点有一个身份模式：

- 以执行者身份（默认）：谁运行蓝图，就检查谁的能力。
- 以蓝图身份：工作区管理员批准「这个蓝图的这个节点可以调用这个操作」。批准后，任何能运行该蓝图的人都能通过它用到服务，即使本人没有这项能力。

约束：

- 批准绑定到节点的具体配置（服务器、服务、操作、固定参数）。节点配置一改，批准失效，需要重新批准。
- 批准、失效、每次以蓝图身份的调用都写审计。
- 数据判定器（第二版 5.2 第 6 层）不受身份模式影响，照常检查。

### 7.4 可见性

服务目录对工作区全体成员可见。没有能力的服务标明原因和找谁开通，只有调用受权限控制。

## 8. 工作区服务管理页

入口有两个：工作区设置，以及蓝图自动化板块。网页端和桌面端都有。

页面回答四个问题：

1. 服务从哪来：哪台服务器，在线状态、负载、版本、来源标示。
2. 谁能调：按成员和权限组分配能力。
3. 谁的蓝图能调：以蓝图身份的批准列表，可以批准和撤销。
4. 现在在跑什么：每个服务的队列。

另有三块：

- 待接收的授权：接收、拒绝、收窄、解除。
- 试用面板：由操作的输入结构生成表单，直接调用一次。
- 用量：成员看自己的，管理员看全工作区的。

## 9. 任务与队列

- 每个服务一条队列，并发上限由清单声明、所有者可以调低。
- 队列里可以看到排队、执行中、进度，发起人和管理者可以取消，管理者可以调整顺序。
- 掉线失败、上线重排、事件通知沿用第二版第 7 章。

## 10. 计量与抵扣

- 计量账本从第一版起记录每个任务：工作区、调用者、蓝图、服务器、服务、操作、计量单位数。只追加。
- 计量单位按结果计，不按显卡时长计。数值尽量由控制面自己得出，主机自报的数字不作为结算依据。
- 扣除：调用消耗的点数从调用者的个人额度扣除。提交任务时冻结，任务成功后结算，失败全额退回。个人额度不足时任务被拒绝，原因码直接说明。
- 付款人规则：

  | 调用方式 | 从谁的个人额度扣 |
  |---------|----------------|
  | 成员直接调用，或在试用面板调用 | 调用者 |
  | 有人运行蓝图，节点以执行者身份调用 | 运行蓝图的人 |
  | 节点以蓝图身份调用 | 蓝图负责人 |
  | 定时或事件触发的蓝图运行，没有人在场 | 蓝图负责人 |
  | 经控制面中转的流量，超出工作区每月免费额度的部分 | 传输者 |

- 由蓝图负责人付款的任务因额度不足被拒绝时，通知蓝图负责人。蓝图负责人能在用量页看到每个蓝图花掉了多少。
- 抵扣：服务器所有者赚到的点数只能抵扣自己在平台的订阅费和云端用量，不出金。
- 主要市场是中国大陆。提现涉及支付资质、代扣税、实名认证，需要法务和财务确认后另行设计，不在本文范围内。

## 11. 首批官方服务

这四个服务用来验证容器抽象是否成立，彼此没有先后。它们都只是一组操作和对应的能力。

| 服务 | 操作举例 | 用到容器的哪些部分 |
|------|---------|-------------------|
| 网络盘（共享盘、私人盘） | 列目录、读、写、改名、删除 | 数据通道（留在服务器上） |
| 本地大模型 | 对话 | 外接驱动、流式文本 |
| LAYA 结构化决策 | 评估 | 图片输入、结构化输出 |
| ComfyUI 生图 | 提交工作流 | 外接驱动、适配程序、队列、进度、数据通道（落到工作区存储） |

网络盘的两种空间：

- 共享盘：服务器上的一块空间，对工作区内持有相应能力的成员可见。
- 私人盘：服务器上只对某一位成员可见的专属空间。其他成员和工作区管理员在目录里看不到它的内容。

两者在容器里是同一个服务的不同空间实例，区别只在能力分配给谁。两种空间都由服务器所有者划出并决定容量；私人盘在划出时指定给哪一位成员。工作区不能申请扩容，沿用第二版 4.6。私人盘的「仅本人可见」是访问控制层面的保证：文件存放在服务器所有者的磁盘上，没有端到端加密，所有者在物理上能接触到这些文件。界面上创建私人盘时要写明这一点。

网络盘不提供公开分享外链，文件只在工作区成员之间流通。对外公开分享会带来内容审核责任，限定在邀请制工作区内可以避开这一点。

## 12. 对现有代码的改动

以下是已核实的现状和对应改动。第二版 PRD 中的待接收流程、决策链、服务目录在后端做到哪一步，尚未逐项核实。

| 位置 | 现状 | 改动 |
|------|------|------|
| 执行主机 | 只支持类 Unix 系统；`browser_*` 和 `model_*` 两组文件各有一套平行的策略、投递、校验 | 抽出通用内核；补 Windows 实现；现有两个模块改写成清单加驱动 |
| 执行主机 | 模型靠手工编辑 `model-policy.json` 配置 | 由界面编辑所有者策略 |
| 控制面 | 模型专用表 `local_server_model_v1`，写死的能力 `local.model.infer` | 通用服务目录；能力由清单注册 |
| 控制面 | 无 | 数据通道、蓝图授权、计量账本、等价组 |
| 网页端 | 无服务管理页 | 新增管理页、通用节点、试用面板 |
| Tauri 壳 | 只面向 macOS 发布，持续集成另在 Ubuntu 上编译 | 增加 Windows 和 Linux 安装包 |
| Swift 客户端 | 本机服务页只有回声模块 | 改为读取通用清单 |

迁移期间，现有的浏览器和模型路径保持可用。

## 13. 实施分层

按容器的层次推进，不按服务推进。一层完成后，四个首批服务中用得到这一层的部分同时可以验证。

| 层 | 内容 | 依赖 |
|----|------|------|
| 一 | 主机跨平台，通用内核，三个系统进持续集成 | 无 |
| 二 | 清单、执行驱动、操作协议 | 一 |
| 三 | 数据通道 | 二 |
| 四 | 服务目录、通用节点、能力分配、蓝图授权、服务管理页、队列 | 二 |
| 五 | 计量账本、抵扣 | 四 |

第三层和第四层可以并行。

每一层的具体要求、验收标准和会话拆分见 `service-container-implementation.md`。所有层开工之前，先定下共享契约（该文第 1 章）。

## 14. 已确认的决定

1. 主机程序跨平台，优先 Windows 和 Linux。
2. 信任靠工作区的邀请制，不靠客户端加密。
3. 容器是通用的，具体服务不是目标。
4. 同时支持官方服务和第三方服务。
5. 操作协议与 MCP 兼容。
6. 容器驱动先支持 Linux。
7. 工作区可以有多台服务器。
8. 蓝图可以作为授权对象；以蓝图身份的批准绑定节点配置，配置改变后重新批准。
9. 管理集中在工作区服务管理页。
10. 主要市场是中国大陆；收益先做抵扣。
11. Windows 和 Linux 的界面使用现有 Tauri 壳。
12. 需要等价组。
13. 调用消耗的点数从调用者的个人额度扣除。
14. 私人盘是服务器上只对某一位成员可见的专属空间。
15. 以蓝图身份的调用，以及没有人在场的蓝图运行，点数都从蓝图负责人的个人额度扣除。
16. 私人盘由服务器所有者划出并决定容量。
17. 无桌面的服务器用设备码登录，另提供登记令牌用于批量部署（4.7）。
18. 模型（包括 LAYA 的权重）通过图形界面配置，面向没有编程基础的用户，格式自动识别（4.6）。

19. 中转流量首版全部经控制面，分服务器和工作区限速；超出工作区每月免费额度的部分从传输者个人额度扣点数（4.4）。
20. 网络盘不提供公开分享外链（第 11 章）。

## 15. 待确认
