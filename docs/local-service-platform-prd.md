# 本机服务平台需求文档

日期：2026-09-23
状态：草案，待产品确认
适用仓库：`Matind_WorkBanch`（桌面客户端）、`Matind_BackendServer`（控制面）、`Matind_Frontend/apps/web`（网页端）
上游契约：`local-server-v1`（`LocalServerContract.swift`、迁移 `20260923000000_local_server_devices.sql`、`20260925000000_local_server_owner_authorization.sql`）

## 1. 一句话

用户的电脑通过桌面客户端变成一台属于他本人的服务器。服务器上装的是一个个可安装、可启停、可卸载的服务模块；所有者把服务授权给任意工作区，工作区再决定内部谁能用、谁能读写；只要这台服务器在线，网页端和桌面端都能调用它。

## 2. 为什么要做

现在的能力都在云端。三类需求云端做不好：

- 需要算力但对延迟和成本敏感的小模型推理。用户自己的机器有 GPU 或高性能 CPU，闲着。
- 涉及本地文件、本地素材、企业内网数据的处理。数据不应该先上传再处理。
- 团队内的临时共享空间。用户已经有一块大硬盘，却要为几百 GB 素材再买云存储。

现有的「本机服务器」只解决了身份、归属和授权这一层：服务器属于登录用户，可以授权给工作区，授权只能收窄不能扩大，短时操作授权由网页签发。它还没有回答「这台服务器到底提供什么」。这份文档回答这个问题。

## 3. 产品思路

### 3.1 三个角色

| 角色 | 是谁 | 能做什么 |
|------|------|----------|
| 服务器所有者 | 登录桌面客户端并启动本机服务的用户 | 安装、卸载、启用、停用服务；把服务授权给工作区；收窄或解除授权；看审计 |
| 工作区管理员 | 持有工作区权限 `local.device.manage` 的成员 | 看本工作区收到了哪些服务器授权；在授权范围内收窄；解除接收；在工作区设置里决定哪些成员组能用、能读写 |
| 服务使用者 | 工作区成员 | 在工作区内调用被授权且自己有权使用的服务：在蓝图里当节点用、在多维表里当字段动作用、在文件管理器里当云盘用 |

同一个人可以同时是三种角色。授权链条仍然是单向的：所有者给出，工作区收窄，成员使用。任何一层都不能越过上一层拿到更多。

### 3.2 客户端是容器和权限管理，服务是模块

桌面客户端本身不实现任何具体服务。它负责：

- 服务器身份（设备密钥、登记、所有者绑定）。
- 服务模块的生命周期（安装、升级、启用、停用、卸载）。
- 授权（授给哪个工作区、给哪些能力、什么版本）。
- 运行时（监听、鉴权、限流、资源配额、日志与审计）。
- 呈现（服务页、服务卡片、健康状态）。

服务是独立打包的模块，声明自己需要什么资源、提供哪些能力、有哪些配置项。加一个新服务不需要改客户端核心。

### 3.3 授权分三层，各管一件事

1. 所有者层：这台服务器上的这个服务，授给了哪些工作区。只有所有者能操作。
2. 工作区接收层：工作区管理员看到收到的授权，可以收窄能力或解除接收。不能扩大。
3. 工作区内部层：在工作区设置里，把「使用某服务」「读写某共享空间」映射到成员组权限。这一层和现有的成员组能力体系（`ws_group_capability`）是同一套东西，只是能力编码由服务动态注册。

任何一次调用必须同时通过三层：授权在、能力没被收窄掉、调用者所在成员组有这个能力。

### 3.4 参照与差异

市面上有两类相近的东西：本地 AI 推理服务器（把模型跑在自己机器上、对外开放接口）和家用 NAS（把硬盘变成局域网或公网可访问的共享盘）。它们解决的是「一个人用自己的机器」。我们的差异在于：服务器天然挂在一个多工作区、多成员的协作系统里，授权和权限是产品的一等公民，调用发生在蓝图、多维表、文件管理器这些已有工作流里，用户不需要面对接口地址和令牌。

## 4. 核心概念

### 4.1 服务器（device）

沿用现有契约。一台电脑一个设备身份，`owner_user_id` 是登录用户。服务器状态：`pending`、`active`、`suspended`、`revoked`、`recovery-required`。

### 4.2 服务模块（service module）

一个可安装的功能单元。每个模块有一份清单：

- `moduleId`：稠密、稳定、反向域名风格，例如 `matind.laya-vision`、`matind.shared-drive`。
- `version`：语义化版本。
- 提供的能力编码列表，形如 `local.service.<moduleId>.<action>`。这些编码进 `capability_registry`，成为工作区可分配的能力。
- 资源需求：磁盘、内存、是否需要 GPU、期望的并发数。
- 配置项：以类型化字段声明，例如模型权重存放路径、共享目录、最大上传体积。
- 健康检查方式。

模块来源分两类：官方模块（随客户端发布或从官方索引安装）和自定义模块（第一阶段不开放）。

### 4.3 服务实例（service instance）

模块装到某台服务器上就是一个实例。实例状态用一个枚举表达，不用多个布尔值：

| 状态 | 含义 |
|------|------|
| `installed` | 已安装，未启用，不接收请求 |
| `starting` | 正在加载模型或初始化 |
| `running` | 可接收请求 |
| `degraded` | 在运行，但健康检查失败或资源告警 |
| `stopped` | 所有者主动停用 |
| `failed` | 启动失败，附错误原因 |
| `removing` | 正在卸载 |

### 4.4 服务授权（service authorization）

现有 `local_server_authorization` 是「服务器对工作区」的授权，能力是固定四个。本需求把能力维度扩展为模块声明的能力编码，授权仍然是「某服务器 → 某工作区 → 一组能力」这一条记录，只是能力集合里出现服务级编码。约束不变：只能收窄、不能扩大、不能改挂账号；最多 8 个能力这条约束需要放宽（见第 9 章）。

### 4.5 短时操作授权（grant）

沿用现有 `local_server_grant`。网页签发，最长 15 分钟，必须落在已有授权内，绑定 `operation_key` 和 `nonce`。每一次服务调用都拿着 grant 来，服务器验证签名与范围后再执行。

### 4.6 共享空间（shared space）

一种特殊的服务模块实例：所有者在本机划出一个目录，授权给工作区后，成为该工作区的本地共享云盘。空间能力细分为 `read`、`write`、`manage`。同一台服务器可以有多个空间，分别授给不同工作区。

## 5. 用户旅程

### 5.1 所有者：把机器变成服务器

1. 在桌面客户端「本机服务」页启动服务器。首次启动生成设备身份并登记。
2. 页面显示服务器卡片：设备标识、在线状态、监听地址、资源概况。
3. 下方是服务卡片列表。未安装的官方模块以「可安装」形态出现。

### 5.2 所有者：安装并启用一个服务

1. 点击「Laya 评估器」卡片上的安装。客户端展示资源需求和下载体积，确认后开始下载模型权重，卡片进入 `starting`。
2. 下载和校验完成后卡片进入 `installed`。所有者点启用，进入 `running`。
3. 卡片展示健康状态、最近调用次数、平均耗时。所有者随时可以停用或卸载。

### 5.3 所有者：授权给工作区

1. 在服务卡片上点「授权」。选择工作区（可以是自己不属于的工作区，通过工作区编号或邀请链接）。
2. 勾选授予的能力。默认勾选模块建议的最小集合。
3. 提交后，控制面写入授权记录，工作区那边收到通知。

### 5.4 工作区管理员：接收并设置

1. 在工作区设置「外部服务」里看到收到的授权：哪台服务器、谁的、什么服务、哪些能力、在不在线。
2. 可以收窄能力或解除接收。
3. 在成员组权限里，把该服务的能力编码分配给成员组。这一步不做，工作区内没有人能用。

### 5.5 成员：在工作流里调用

- 蓝图：出现「本机服务」类节点，选择工作区已接收且自己有权的服务实例，配置输入输出。运行时由控制面签发 grant，节点携带 grant 调用服务器。
- 多维表：字段动作里出现「用 Laya 评估」之类的动作，对图片字段批量打分，结果写回字段。
- 文件管理器：出现「共享空间」卷，浏览、上传、下载受 `read`/`write` 能力约束。
- 网页端与桌面端行为一致，差别只在于网页端所有调用都经控制面中转（见 6.3）。

### 5.6 服务器离线

- 服务卡片显示离线；工作区端调用入口置灰并说明原因；蓝图节点运行时报「服务器离线」并可配置重试或跳过。
- 共享空间离线时文件列表保留最近一次缓存的目录结构，标记为不可用。

## 6. 功能需求

### 6.1 本机服务页（桌面客户端）

- 独立页面，和「自动化」同级，从菜单和标签栏都能进。
- 顶部为服务器卡片：身份、状态、启动/停止、资源占用（CPU、内存、GPU、磁盘）。
- 服务卡片网格。每张卡片：图标、名称、版本、状态徽章、健康、资源占用、授权工作区数。卡片上的动作按状态呈现：安装 / 启用 / 停用 / 卸载 / 授权 / 设置。
- 卡片点开进入服务详情：配置项、授权列表、调用日志、错误信息。
- 官方模块不可用（平台停用、版本不兼容）时卡片锁定并说明原因。
- 每个改变状态或授权的动作都需要二次确认；启用会开始接收请求、卸载会删除模型文件，确认文案要写清后果。

### 6.2 服务模块生命周期

- 安装：校验清单签名，下载资源，校验哈希，落盘到客户端管理的目录。
- 升级：并存新版本，切换后旧版本延迟清理；授权记录带 `moduleVersion`，工作区能看到版本变化。
- 启用 / 停用：状态机见 4.3；停用不影响授权记录，工作区端看到「已停用」。
- 卸载：先停用，检查是否仍有活动授权并提示，再删除文件；共享空间卸载不删除用户目录内容。
- 崩溃恢复：客户端重启后按上次状态恢复；连续失败三次进入 `failed` 并停止自动重试。

### 6.3 调用通道

现有契约要求服务器只监听 `127.0.0.1`。「网页端也能调」意味着必须有一条从云端到本机的通道。方案：

- 服务器启动后向控制面建立一条出站长连接（WebSocket 或 HTTP/2 流），控制面把调用请求沿这条连接下发，服务器把结果沿同一连接回传。
- 服务器不开任何入站端口，不需要公网 IP，不需要用户配置路由器。
- 网页端和桌面端统一向控制面发起调用；控制面校验三层授权、签发 grant、选择在线服务器、转发。
- 大文件（共享空间上传下载、生成的图片和视频）走同一连接的流式分帧，控制面不落盘，只做透传与限速。
- 桌面端调用自己这台机器上的服务时，允许直连回环地址以节省一跳；权限校验仍由 grant 保证。

### 6.4 授权与权限

- 所有者授权：授给工作区，选择能力，可选到期时间。
- 工作区接收：查看、收窄、解除。
- 工作区内部：能力编码进入成员组权限矩阵；服务卸载或授权解除时，相关能力自动从矩阵中消失并留下审计。
- 每一次调用留审计：谁、哪个工作区、哪个服务、哪个能力、耗时、结果。审计只追加。

### 6.5 资源与配额

- 所有者为每个服务实例设置并发上限和单次任务最大时长。
- 所有者为每个共享空间设置容量上限和单文件上限。
- 服务器总资源到阈值时新请求排队，队列长度可配置，超过则拒绝并返回明确原因。

## 7. 首批服务模块

### 7.1 Laya 评估器（`matind.laya-vision`）

Laya Vision 是一个小型视觉语言模型（SmolVLM-256M 骨干），一次前向传播对一张图片加可选文字回答一组类型化问题：多选（`choice`）、是否概率（`noul`）、按用户自定义量表打分（`score`），输出带校准概率，无文本生成。模型很小，普通笔记本 CPU 就能跑。

产品形态：

- 工作区里的「评估模板」：一组问题及量表。
- 多维表动作：对图片字段按模板批量评估，结果写入数字或选项字段。
- 蓝图节点：输入图片与模板，输出结构化答案，用于后续分支。
- 能力编码：`local.service.matind.laya-vision.evaluate`。

限制要在界面上明说：模型领域偏日常照片与图表，专业领域需要自训练权重；一次一张 512 像素图片。

### 7.2 图片生成 / 视频生成（`matind.image-gen`、`matind.video-gen`）

- 按机器性能分档：客户端检测 GPU 显存与统一内存，只向所有者推荐机器能跑的模型档位。
- 产物写回工作区文件管理器或多维表附件字段，不留在服务器本地。
- 视频生成是长任务，必须异步：提交返回任务标识，进度通过同一条长连接推送，蓝图节点用等待节点接收。
- 能力编码：`local.service.matind.image-gen.generate`、`local.service.matind.video-gen.generate`、`...cancel`。

### 7.3 共享空间（`matind.shared-drive`）

- 所有者选择本机目录，设置容量上限。
- 授权给工作区后，在该工作区文件管理器里以一个卷出现。
- 能力：`read`、`write`、`manage`（改容量、清理）。
- 文件元数据（名称、大小、哈希、修改时间）同步到控制面以便离线时可浏览；文件内容只在服务器。
- 版本与回收站：第一阶段只做回收站，不做版本。

## 8. 非目标

- 不做自定义模块的公开市场。第一阶段只有官方模块。
- 不做服务器之间的负载均衡或高可用。一个工作区可以接收多台服务器的授权，调用时按在线状态选择，不做自动故障转移。
- 不做端到端加密的共享空间。传输加密由长连接 TLS 保证，静态数据以所有者机器的磁盘安全为界。
- 不允许服务器在登记时绑定工作区，也不允许改挂到别的账号。这是现有契约的红线，保持。

## 9. 对现有契约的改动

| 项 | 现状 | 改动 |
|----|------|------|
| 能力编码 | 固定四个 `local.*` | 增加模块动态注册的 `local.service.<moduleId>.<action>`；`LocalCapability` 从枚举改为带注册表的值类型 |
| 授权能力上限 | 1 到 8 个 | 放宽到 32 个，或者改为按模块分组存储 |
| 服务器只监听回环 | 是 | 保持；新增出站长连接到控制面作为唯一的远程调用入口 |
| `capability_registry` | 手工插入 | 服务模块安装时由控制面按清单注册，卸载后标记停用 |
| 审计 | 设备与授权层面 | 增加调用级审计表，只追加 |
| 桌面「自动化」页 | 占位 | 不在本需求范围；本机服务页是新增的同级页面 |

## 10. 分阶段

| 阶段 | 内容 | 验收 |
|------|------|------|
| S0 | 本机服务页、服务器卡片、状态机、安装/启用/停用/卸载流程、官方模块索引 | 装一个空壳「回声」模块，全生命周期可走通，状态与审计正确 |
| S1 | 控制面长连接通道、grant 走通道、网页端能调用回声模块 | 网页端从一个工作区调到另一台机器上的回声模块，服务器无入站端口 |
| S2 | 服务级能力注册、三层授权贯通、工作区设置里的成员组映射 | 未分配成员组的成员调用被拒；收窄后立即生效 |
| S3 | Laya 评估器：多维表动作与蓝图节点 | 100 张图片批量评估在 CPU 上完成，结果写回字段 |
| S4 | 共享空间：文件管理器卷、读写权限、回收站 | 两个工作区各自挂一块空间，权限互不越界 |
| S5 | 图片生成、视频生成异步任务 | 按机器档位安装，任务进度实时可见，可取消 |

每个阶段单独可交付，前一个阶段没有验收通过不开始下一个。

## 11. 待确认

1. 所有者把服务授给自己不在其中的工作区：该工作区管理员是否需要先「接受」才生效，还是授权即生效、管理员只能事后解除。建议先接受再生效。
2. 共享空间的容量上限由所有者定，工作区能否申请扩容；是否需要一条请求流程。
3. 视频生成等长任务在服务器关机时的处理：任务失败还是排队等服务器上线。建议失败并通知发起人。
4. 模块清单签名的密钥由谁保管；官方索引是否与后端一起部署。
5. 同一工作区收到两台服务器同一模块的授权时，调用方是否可以指定用哪台。建议蓝图节点可以指定，多维表动作自动选在线且负载低的。
