## 1. 一句话

用户的电脑通过桌面客户端变成一台属于他本人的服务器。服务器上装的是一个个可安装、可启停、可卸载的服务模块。所有者把服务授权给自己所在的工作区，工作区再决定内部谁能用、谁能读写。只要这台服务器在线，网页端和桌面端都能调用它。

## 2. 为什么要做

现在的能力都在云端。三类需求云端做不好：

- 需要算力、但对延迟和成本敏感的小模型推理。用户自己的机器有 GPU 或高性能 CPU，平时闲着。
- 涉及本地文件、本地素材、企业内网数据的处理。这些数据不应该先上传再处理。
- 团队内的共享空间。用户已经有一块大硬盘，却要为几百 GB 素材再买云存储。

现有的「本机服务器」只解决了身份、归属和授权这一层：服务器属于登录用户，可以授权给工作区，授权只能收窄不能扩大，短时操作授权由网页签发。它还没有回答「这台服务器到底提供什么」。这份文档回答这个问题。

## 3. 产品思路

### 3.1 四个角色

| 角色 | 是谁 | 能做什么 |
|------|------|----------|
| 服务器所有者 | 登录桌面客户端并启动本机服务的用户 | 全部：安装、卸载、启用、停用服务；授权；任命和撤销服务器管理者；轮换和吊销设备密钥 |
| 服务器管理者 | 所有者任命的用户 | 在所有者划定的范围内代管：服务的启停与配置、授权的收窄与解除、任务的重试与取消。不能任命别人，不能转移所有权 |
| 工作区管理员 | 在接收方工作区持有 `local.device.manage` 的成员 | 接收或拒绝授权；在授权范围内收窄；解除接收；在成员组权限里决定谁能用、谁能读写 |
| 服务使用者 | 工作区成员 | 在工作流里调用被授权、且自己有权使用的服务 |

同一个人可以同时是多种角色。授权链条是单向的：所有者给出，工作区收窄，成员使用。任何一层都不能越过上一层拿到更多。

### 3.2 客户端是容器和权限管理，服务是模块

桌面客户端本身不实现任何具体服务。它负责：

- 服务器身份：设备密钥、登记、所有者绑定。
- 服务模块的生命周期：安装、升级、启用、停用、卸载。
- 授权：授给哪个工作区，给哪些能力，对应哪个版本。
- 运行时：到控制面的长连接、鉴权、限流、资源配额、日志与审计。
- 呈现：本机服务页、服务卡片、健康状态、任务队列。

服务是独立打包的模块，声明自己需要什么资源、提供哪些能力、有哪些配置项。加一个新服务不需要改客户端核心。

### 3.3 参照与差异

相近的产品有两类：本地 AI 推理服务器（把模型跑在自己机器上，对外开放接口），和家用 NAS（把硬盘变成共享盘）。它们解决的是「一个人用自己的机器」。

我们的差异有三点：

- 服务器天然挂在一个多工作区、多成员的协作系统里，授权和权限是一等公民。
- 调用发生在蓝图、多维表、文件管理器这些已有工作流里，用户不面对接口地址和令牌。
- 服务上线即注册进工作区的节点系统，AI 搭蓝图时能直接选用。

## 4. 核心概念

### 4.1 服务器

沿用现有契约。一台电脑一个设备身份，`owner_user_id` 是登录用户。服务器状态沿用 `pending`、`active`、`suspended`、`revoked`、`recovery-required`。另有一个在线维度，由长连接心跳决定：`online`、`offline`。这两个维度互相独立，不合并成一个状态。

### 4.2 服务模块

一个可安装的功能单元，每个模块有一份清单：

- `moduleId`：稳定、反向域名风格，例如 `matind.laya-vision`、`matind.shared-drive`。
- `version`：语义化版本。
- 能力：形如 `local.service.<moduleId>.<action>` 的能力编码列表。每个能力声明一个类别：
  - 调用类：使用服务，例如评估、生成。
  - 数据类：读写服务托管的数据，例如共享空间的读、写。
  - 管理类：修改服务在该工作区的配置，例如清理回收站。
- 资源需求：磁盘、内存、是否需要 GPU、期望并发。
- 配置项：用类型化字段声明，例如模型存放路径、共享目录、单文件上限。
- 健康检查方式。
- 节点描述：服务在蓝图里暴露成哪些节点，每个节点的输入、输出、是否为长任务（见第 8 章）。

### 4.3 服务实例

模块装到某台服务器上就是一个实例。实例状态用一个枚举表达，卡片上的可用动作由状态决定：

| 状态 | 含义 | 卡片上可用的动作 |
|------|------|------------------|
| `available` | 官方索引里有，本机未安装 | 安装 |
| `installing` | 正在下载和校验 | 取消 |
| `installed` | 已安装，未启用，不接收请求 | 启用、卸载、设置 |
| `starting` | 正在加载模型或初始化 | 无 |
| `running` | 可接收请求 | 停用、授权、设置 |
| `degraded` | 在运行，但健康检查失败或资源告警 | 停用、查看原因 |
| `stopped` | 所有者或管理者主动停用 | 启用、卸载、设置 |
| `failed` | 启动失败，附错误原因 | 重试、卸载、查看原因 |
| `removing` | 正在卸载 | 无 |

### 4.4 服务授权

现有 `local_server_authorization` 是「服务器对工作区」的授权，能力是固定的四个。本设计把能力维度扩展为模块声明的能力编码。一条授权仍然是「某服务器 → 某工作区 → 一组能力」，约束不变：只能收窄、不能扩大、不能改挂账号。

授权新增一个接收状态，由 `authorization.status` 扩展而来：`pending`（待接收）、`active`、`suspended`、`revoked`、`declined`（接收方拒绝）。

### 4.5 短时操作授权

沿用现有 `local_server_grant`：网页签发，最长 15 分钟，必须落在已有授权内，绑定 `operation_key` 和 `nonce`。每一次服务调用都拿着 grant 来，服务器验证签名与范围后再执行。

### 4.6 共享空间

一种特殊的服务模块实例：所有者在本机划出一个目录，授权给工作区后，成为该工作区的本地共享云盘。

- 容量由所有者定。这是硬件配置，工作区不能申请扩容，第一阶段不设任何申请流程。
- 能力分三级：`read`、`write`、`manage`。
- 同一台服务器可以有多个空间，分别授给不同工作区。

### 4.7 工作区服务目录

服务器上线后，控制面按它当前的有效授权，把其上所有 `running` 的服务和空间注册进对应工作区的服务目录。服务目录是工作区节点系统的数据来源：

- 蓝图面板里的「本机服务」分类，从这里生成节点。
- 文件管理器里的共享空间卷，从这里列出。
- 工作区设置的成员组权限里，服务能力从这里出现。

服务器离线时，目录条目保留并标记为离线；授权解除或服务卸载时，条目移除。

### 4.8 服务任务

每一次服务调用都是一个任务。短调用（一次 Laya 评估）是同步任务，长调用（视频生成）是异步任务。两者共用同一张表和同一个状态机，见第 7 章。

## 5. 授权与权限架构

### 5.1 授权范围：只能授给所有者在其中的工作区

所有者或管理者只能把服务授权给自己是成员的工作区。这样做有两个好处：

- 授权对象可见，不再需要手输工作区编号。
- 杜绝把服务器塞进陌生工作区的滥用。

随之而来的问题是：所有者在那个工作区里的权限可能很有限，比如他只是普通成员，没有读写权限。授权之后，他自己却用不了自己的服务。这个问题不能靠「所有者特判」零散补洞，要靠一套可组合的决策架构解决。

### 5.2 决策链：每一层是一个独立的判定器

一次调用是否放行，由一条判定器链决定。每个判定器只看自己那一层，返回三种结果之一：允许、拒绝（附原因码）、不适用。规则是：

- 任一拒绝即拒绝。
- 至少要有一个「成员层」判定器给出允许。
- 拒绝原因码是枚举，直接驱动界面文案。

| 顺序 | 判定器 | 看什么 | 典型拒绝原因 |
|------|--------|--------|--------------|
| 1 | 服务器判定器 | 设备状态 `active`，且在线 | `device_suspended`、`device_offline` |
| 2 | 实例判定器 | 服务实例为 `running` 或 `degraded` | `service_stopped` |
| 3 | 授权判定器 | 授权为 `active`，且能力在授权集合内 | `authorization_revoked`、`capability_not_granted` |
| 4 | 成员组判定器 | 调用者所在成员组持有该能力编码 | `capability_not_assigned` |
| 5 | 提供者席位判定器 | 调用者是该服务器的所有者或管理者（见 5.3） | 不会拒绝，只会允许或不适用 |
| 6 | 数据判定器 | 本次调用读写的工作区资源，调用者是否有权 | `dataset_write_denied`、`file_read_denied` |

第 4 与第 5 层都属于成员层，任一允许即可。第 6 层由服务模块在清单里声明自己触碰哪类资源，平台据此挂上对应的数据判定器。新增一种服务，只需要声明它的资源范围，不需要改决策链本身。

### 5.3 提供者席位

所有者（以及他任命的管理者）在接收方工作区里，自动持有一个「提供者席位」：

- 对他提供的服务，自动拥有该授权集合内的调用类能力。
- 对他提供的共享空间，自动拥有 `read`、`write`、`manage`。空间的文件本来就在他的磁盘上，这么做是如实反映物理事实，而不是额外开特权。
- 提供者席位不带任何工作区数据权限。所有者用 Laya 评估某张多维表，写回结果时仍然要过第 6 层：他没有这张表的写权限，就写不回去。

这样就把两件事分开了：服务能不能用，由「你是提供者」决定；工作区的数据能不能碰，由工作区决定。

提供者席位在成员列表里可见，带「提供者」徽章。工作区管理员不能单独拿掉它；如果不接受这台服务器的提供者使用自己的服务，管理员可以解除接收整条授权。所有者如果不再需要这个工作区用他的机器，可以撤销授权。双方的退出权对等。

### 5.4 接收：授权先待接收，再生效

- 授权提交后进入 `pending`，工作区管理员在设置里接收或拒绝。
- 如果提交授权的人本身在该工作区持有 `local.device.manage`，接收自动完成。所有者恰好是工作区管理员时，不需要自己批自己。
- 接收之前，服务不进入工作区服务目录，也不出现在成员组权限里。

### 5.5 工作区内部：服务能力进入成员组权限

服务能力编码进入现有的 `capability_registry`，在工作区设置的「权限组」对话框里以「本机服务」分组出现，按服务器、服务两级展开。和现有能力一样勾选、保存到 `ws_group_capability`，不另起一套权限表。

- 授权收窄或解除时，被移除的能力从所有成员组里自动失效，并留下审计。
- 服务卸载后，其能力编码在注册表里标记为停用，不物理删除，以保留审计的可读性。

## 6. 调用通道

现有契约要求服务器只监听 `127.0.0.1`。「网页端也能调」意味着必须有一条从云端到本机的通道：

- 服务器启动后向控制面建立一条出站长连接，控制面把调用请求沿这条连接下发，服务器把结果沿同一连接回传。
- 服务器不开任何入站端口，不需要公网 IP，不需要用户配置路由器。
- 这条长连接同时承担在线心跳。心跳中断超过阈值，控制面把服务器标为 `offline`，并触发第 7 章的离线处理。
- 网页端和桌面端都向控制面发起调用。控制面走一遍第 5 章的决策链，签发 grant，选择服务器，转发。
- 大文件（共享空间上传下载、生成的图片和视频）走同一连接的流式分帧，控制面不落盘，只做透传与限速。
- 桌面端调用自己这台机器上的服务时，允许直连回环地址，省一跳。权限校验仍由 grant 保证，和远程调用走同一条决策链。

现有 `ingest_audit` 已经是一个本机主动回传控制面的入口。长连接应以这一条为起点扩展，不另开第二套回传通道。

## 7. 任务、失败与重排

### 7.1 任务状态机

| 状态 | 含义 |
|------|------|
| `queued` | 已提交，等服务器接单 |
| `dispatched` | 已下发到服务器 |
| `running` | 服务器在执行，异步任务会持续回报进度 |
| `succeeded` | 完成，产物已写回 |
| `failed` | 失败，附原因码：`device_offline`、`service_error`、`timeout`、`denied`、`cancelled_by_owner` |
| `requeued` | 失败后被重新排队，产生一次新的尝试 |
| `cancelled` | 发起人或提供者取消 |

每个任务记录来源：蓝图运行（运行标识和节点标识）、多维表动作（表、行、字段）或手动调用。重排和写回都按来源处理。

### 7.2 服务器掉线

1. 心跳中断，控制面把服务器标为 `offline`。
2. 该服务器上所有 `dispatched` 和 `running` 的任务立即转为 `failed`，原因 `device_offline`，并直接报失败，不做静默等待。
3. `queued` 任务保持排队，不下发。
4. 发送「服务器离线」和「任务失败」事件，见 7.4。

### 7.3 服务器重新上线

1. 长连接恢复，控制面把服务器标为 `online`，服务目录恢复可用。
2. 扫描该服务器上因 `device_offline` 失败、且满足重排条件的任务，转为 `requeued`，生成新的尝试重新下发。重排条件：
   - 未被发起人取消；
   - 未超过尝试上限（默认 3 次）；
   - 未超过任务有效期（默认 24 小时，模块可覆盖）；
   - 发起人对服务的权限仍然有效（重排前重新走一遍决策链）。
3. 因其他原因失败的任务不自动重排，只能手动重试。
4. 发送「服务器上线」和「任务已重排」事件。

来自蓝图运行的任务：节点在任务失败时向运行报失败；任务重排并成功后，运行从该节点恢复，不从头重跑。这要复用现有 `blueprint_outbox` 的租约、尝试次数和退避机制，不另建一个任务队列。

### 7.4 事件与通知

现有系统有两套通知：遗留的 `notify` 表已标注废弃，现行的是 `automation_inbox_v1` 收件箱（按 `owner_id` 持久化）加 `automation_notification_delivery_v1` 投递记录；推送渠道有 Web Push 和邮件，实时通道是 IM 的 WebSocket。缺的是一个「事件 → 收件人」的解析层，现在每个调用方自己决定发给谁。

本设计补上这一层，不新增通知表：

- 事件定义：每种事件在代码里声明一次，包括事件类型、收件人规则、是否聚合、默认渠道。
- 收件人规则是枚举组合，不是写死的用户列表：
  - `initiator`：任务发起人；
  - `provider`：服务器所有者及管理者；
  - `workspace_admins`：接收方工作区持有 `local.device.manage` 的成员；
  - `blueprint_steward`：来源蓝图的负责人。
- 解析后，每个收件人写一条收件箱记录。在线的用户通过现有 WebSocket 信封实时推送；离线的用户按投递规则走 Web Push 或邮件。
- 聚合：同一次离线导致的大量失败，对每个收件人只发一条，附失败任务数和列表入口，不刷屏。

首批事件：

| 事件 | 收件人 | 聚合 |
|------|--------|------|
| 服务器离线 | provider、workspace_admins | 每次离线一条 |
| 服务器上线 | provider、workspace_admins | 每次上线一条 |
| 任务失败 | initiator、blueprint_steward | 按离线事件聚合 |
| 任务已重排 | initiator | 按上线事件聚合 |
| 任务最终失败（超过上限或过期） | initiator、provider | 不聚合 |
| 服务降级 | provider | 每次状态变化一条 |
| 授权待接收 | workspace_admins | 不聚合 |
| 授权已接收、已拒绝、被收窄、被解除 | provider | 不聚合 |
| 共享空间容量将满 | provider、workspace_admins | 每个阈值一条 |

这个事件层对本机服务之外也可复用。蓝图人工审批、闹钟提醒等已有通知可以逐步迁到同一层，但不在本需求范围内。

## 8. 节点注册与选择

### 8.1 上线即注册

服务器上线、服务处于 `running` 时，服务模块清单里的节点描述随之进入工作区服务目录。蓝图面板的「本机服务」分类，以及 AI 搭蓝图时可用的节点清单，都从服务目录生成。

这里的节点是服务端执行的节点，和现有服务端 `NodeRegistry` 的执行语义一致：前端只画节点、编辑参数，执行在控制面调度，最终经长连接下发到服务器。

### 8.2 同一服务有多个来源

同一工作区可能从两台服务器接收到同一模块。注册时两份都存在，节点上带「来源服务器」参数：

- 用户手动搭蓝图时，节点参数面板里可以选服务器。默认选当前在线且负载较低的一台。
- AI 搭蓝图时，自动任选其一，并在节点上注明选了哪台，用户可以改。
- 选定的服务器离线时，节点运行报 `device_offline`，不自动切到另一台。切换来源会改变结果（不同机器、不同模型版本），要由用户明确决定。

## 9. 首批服务模块

### 9.1 Laya 评估器 `matind.laya-vision`

Laya Vision 是一个小型视觉语言模型（SmolVLM-256M 骨干）。一次前向传播，对一张图片加可选文字回答一组类型化问题：多选（`choice`）、是否概率（`noul`）、按用户自定义量表打分（`score`）。输出带校准概率，不生成文字。模型很小，普通笔记本 CPU 就能跑。

产品形态：

- 评估模板：工作区里保存的一组问题及量表。
- 蓝图节点：输入图片和模板，输出结构化答案，用于后续分支。
- 多维表：不新造一种字段级远程调用。沿用现有的按钮列加蓝图绑定：提供一个官方蓝图模板「图片字段 → Laya 评估 → 写回字段」，用户在表上一键套用。
- 能力：`local.service.matind.laya-vision.evaluate`（调用类）。

限制要在界面上明说：模型擅长日常照片和图表，专业领域需要自训练权重；每次处理一张图，缩放为 512 像素。

### 9.2 图片生成 `matind.image-gen`、视频生成 `matind.video-gen`

- 按机器性能分档：客户端检测 GPU 显存与统一内存，只向所有者推荐机器能跑的模型档位。
- 产物写回工作区文件管理器或多维表附件字段，不留在服务器本地。
- 视频生成是异步任务：提交后立即返回任务，进度经长连接推送，蓝图里用等待节点接收结果。
- 能力：`...image-gen.generate`、`...video-gen.generate`（调用类），`...cancel`（管理类）。

### 9.3 共享空间 `matind.shared-drive`

- 所有者选择本机目录，设置容量上限。
- 授权并被接收后，在该工作区文件管理器里以一个卷出现。
- 文件元数据（名称、大小、哈希、修改时间）同步到控制面，离线时可以浏览目录；文件内容只在服务器上。
- 第一阶段只做回收站，不做版本。

## 10. 前端设计

### 10.1 设计原则

- 一个概念一个入口。服务在桌面端只在「本机服务」页管理，授权接收在网页端只在工作区设置里处理，不在多处放同样的开关。
- 状态驱动动作。卡片上只出现当前状态允许的动作，不出现灰掉的一排按钮。
- 拒绝原因说人话。第 5.2 节的原因码一一对应界面文案，并附下一步。例如「这台服务器离线，所有者上线后任务会自动重排」，不写「请求失败」。
- 复用现有组件。网页端用现有的文件卡片、`useConfirm` 确认框、权限组对话框和文件类型注册表；桌面端用现有的标签页和卡片样式，不新建设计体系。

### 10.2 桌面端：本机服务页

入口：新增一种标签页，和「自动化」同级，从菜单和标签栏都能打开。现在设置页里的「本机服务器」分区迁到这里，设置页只保留一行入口链接。

页面自上而下分四块：

1. 服务器卡片：设备名、所有者、在线状态、到控制面的连接状态、CPU、内存、GPU、磁盘占用，启动或停止按钮。
2. 服务：服务卡片网格。
3. 共享空间：空间卡片网格，和服务卡片同构，多显示已用和总容量。
4. 任务：最近任务列表，按状态筛选，可以重试或取消。

服务卡片的组成：

- 图标、名称、版本。
- 状态徽章，取值见 4.3。
- 一行健康信息：运行中显示最近一小时调用数和平均耗时；降级或失败显示原因。
- 授权摘要：「已授权 3 个工作区，1 个待接收」。
- 动作区：按 4.3 的状态表呈现。

卡片点开是服务详情，分五个分页：

- 概览：状态、资源、健康历史。
- 配置：由清单的配置项自动生成表单。
- 授权：这项服务授给了哪些工作区、每个的状态和能力，以及授权和收窄入口。
- 任务：这项服务的任务。
- 日志：运行日志，只读。

授权对话框：

- 工作区是一个下拉列表，只列出操作者所在的工作区。取代现在手输工作区编号的文本框。
- 能力是复选框，按调用类、数据类、管理类分组，默认勾选模块建议的最小集合。
- 可选到期时间。
- 底部说明：操作者在该工作区若持有 `local.device.manage`，接收自动完成；否则等待工作区管理员接收。

管理者：服务器卡片上有「管理者」入口，所有者在这里添加、移除管理者，并选择管理者可以操作的范围。管理者打开同一页面时，超出范围的动作不出现。

安装流程：

1. 点「安装」后弹出资源检查：模块需要多少磁盘和内存、是否需要 GPU，以及本机是否满足。不满足时写明差什么，安装按钮不可用。
2. 确认后卡片进入 `installing`，显示下载进度，可以取消。下载完成后用内置的平台公钥校验清单签名和文件哈希；校验失败时删除已下载文件，卡片回到 `available`，并写明「安装包校验失败，未安装」。
3. 完成后进入 `installed`，提示「启用后才会接收请求」。

凡是改变状态或授权的动作都要二次确认。确认文案写清后果：启用会开始接收请求；卸载会删除模型文件、解除所有授权；共享空间卸载不删除目录里的文件。

### 10.3 网页端：工作区设置

在现有工作区设置页「成员与权限」和「企业信息」之间，新增「外部服务」分区：

- 待接收：列出待接收的授权，显示提供者、服务器、服务和能力，每条有「接收」「拒绝」。
- 已接收：按服务器分组，列出服务和空间。每条显示在线状态、版本、能力，并提供「收窄」「解除接收」。
- 离线的服务器在分组标题上标出，附最后在线时间。

权限组对话框：现有能力字典里新增「本机服务」分组，按服务器、服务两级折叠，复选框和现有能力一致。未接收的服务不出现。

成员列表：提供者席位的成员名旁显示「提供者」徽章，鼠标悬停说明他为何能用这些服务、为何仍受工作区数据权限约束。

### 10.4 网页端：在工作流里使用

蓝图面板：

- 节点面板新增「本机服务」分类，节点从工作区服务目录生成。离线服务的节点仍可拖入，但带离线标记。
- 节点参数面板顶部是「来源服务器」选择器，只在同一服务有多个来源时出现，每个选项显示在线状态和负载。
- AI 搭建的蓝图里，自动选中的来源在节点上显示，可以修改。

多维表：

- 表设置的自动化面板里，出现本机服务相关的官方蓝图模板，例如「图片字段 → Laya 评估 → 写回」。套用后生成一个按钮列和一条蓝图绑定，沿用现有按钮事件机制。
- 行上的运行状态用现有的写入状态提示展示：排队中、运行中、失败原因。

文件管理器：

- 共享空间通过新增一个文件类型描述符接入现有文件类型注册表，在简易文件管理器里多一个「共享空间」标签。
- 无 `write` 能力时不显示上传和新建，而不是点了再报错。
- 服务器离线时，目录可以浏览，文件打开和下载不可用，并说明原因。

### 10.5 通知与任务入口

网页端目前没有一个读取现行收件箱的通知中心，桌面端的通知中心还在用已废弃的 `/notification/*` 接口。本需求顺带把两端统一到 `automation_inbox_v1`：

- 网页端顶栏增加铃铛，打开收件箱抽屉；桌面端现有铃铛改接收件箱接口。
- 收件箱条目按事件类型渲染。任务类条目点开是任务详情抽屉：状态、尝试记录、失败原因、重试或取消。
- 聚合条目（「服务器离线，12 个任务失败」）展开是任务列表。
- 实时更新走现有 IM WebSocket 信封，不另开一条连接。

### 10.6 状态与文案对照

| 场景 | 界面表现 | 文案要点 |
|------|----------|----------|
| 服务器离线 | 卡片和节点加离线标记，调用入口不可用 | 离线多久；所有者上线后失败任务会自动重排 |
| 服务已停用 | 节点不可运行，表格按钮不可点 | 由所有者停用，联系谁 |
| 能力未分配 | 入口不出现 | 在工作区设置里给成员组分配 |
| 能力未授予 | 入口不出现；管理员视角显示「授权中未包含」 | 需提供者扩大授权，工作区不能自行扩大 |
| 数据无权 | 运行到写回时失败 | 服务可以用，但没有这张表或这个文件的写权限 |
| 授权待接收 | 管理员看到待办，普通成员看不到服务 | 谁提交的，给了什么能力 |
| 任务最终失败 | 收件箱条目，任务详情 | 尝试了几次，最后一次的原因，可以手动重试 |

## 11. 非目标

- 不做自定义模块的公开市场，也不支持所有者自签的私有模块。只安装平台签名的官方模块。
- 不做服务器之间的自动故障转移。同一服务有多个来源时由用户选择，见 8.2。
- 不做工作区申请扩容的流程。共享空间容量由所有者决定。
- 不做端到端加密的共享空间。传输加密由长连接 TLS 保证，静态数据以所有者机器的磁盘安全为界。
- 不允许服务器在登记时绑定工作区，也不允许改挂到别的账号。这是现有契约的红线，保持。

## 12. 对现有契约与系统的改动

| 项 | 现状 | 改动 |
|----|------|------|
| 能力编码 | 固定四个 `local.*` | 增加模块注册的 `local.service.<moduleId>.<action>`；桌面端 `LocalCapability` 从固定枚举改为「平台能力 + 模块能力」的值类型 |
| 授权能力上限 | 1 到 8 个 | 放宽到 32 个 |
| 授权对象 | 任意工作区编号 | 仅限操作者所在的工作区 |
| 授权状态 | `active`、`suspended`、`revoked` | 增加 `pending`、`declined` |
| 服务器管理者 | 无 | 新增管理者表，记录范围、任命人和任命时间 |
| 服务器只监听回环 | 是 | 保持；新增出站长连接作为唯一的远程调用入口，从 `ingest_audit` 扩展 |
| `capability_registry` | 手工插入 | 授权被接收时按清单注册，服务卸载后标记停用 |
| 工作区服务目录 | 无 | 新增，由控制面按授权与在线状态维护 |
| 服务任务 | 无 | 新增任务表；重排复用 `blueprint_outbox` 的租约与尝试机制 |
| 通知 | 遗留 `notify` 与 `automation_inbox_v1` 并存 | 新增事件到收件人的解析层，统一写入 `automation_inbox_v1`；两端通知中心改接收件箱 |
| 审计 | 设备与授权层面 | 增加调用级审计，只追加 |
| 桌面「自动化」页 | 占位 | 不在本需求范围；本机服务页是新增的同级页面 |

## 13. 分阶段

| 阶段 | 内容 | 验收 |
|------|------|------|
| S0 | 本机服务页、服务器卡片、实例状态机、安装、启用、停用、卸载；官方索引；用一个空壳「回声」模块 | 回声模块全生命周期走通，状态与审计正确 |
| S1 | 出站长连接、在线心跳、grant 走长连接；网页端调用回声模块 | 网页端调到另一台机器上的回声模块，服务器无入站端口 |
| S2 | 授权范围限制、待接收流程、决策链、提供者席位、服务能力进入权限组 | 没有分配能力的成员被拒；提供者能用自己的服务但写不了无权的表；收窄立即生效 |
| S3 | 服务任务表、掉线失败、上线重排、事件解析层、两端收件箱 | 拔网线：任务立即失败并收到一条聚合通知；恢复后任务自动重排并完成 |
| S4 | 工作区服务目录、蓝图「本机服务」节点、来源选择；Laya 评估器与多维表模板 | 在 CPU 上批量评估 100 张图，结果写回字段；AI 搭蓝图能选到节点 |
| S5 | 共享空间：文件类型接入、读写权限、离线浏览、回收站 | 两个工作区各挂一块空间，权限互不越界 |
| S6 | 图片生成、视频生成异步任务 | 按机器档位安装，进度实时可见，可以取消 |

每个阶段单独可交付，前一个阶段验收没通过，不开始下一个。

## 14. 已确认的决定

1. 所有者只能把服务授权给自己在其中的工作区。所有者权限不足的问题，由第 5 章的决策链和提供者席位解决。
2. 共享空间的容量由所有者决定，工作区不能申请。暂不设计申请流程。
3. 服务器掉线时任务直接报失败；上线后自动重新排队并重启失败的任务；相关事件发给相关人员，事件层统一建在现有收件箱上。
4. 服务器由所有者和他任命的管理者管理；服务器上线后，其全部可用服务和空间注册进已接收授权的工作区节点系统。
5. 同一服务有多个来源时，用户手动选择；AI 搭蓝图时自动任选其一。
6. 模块安装包只由 Matind 平台签名。客户端内置平台公钥，只安装清单签名校验通过、且文件哈希与清单一致的模块。所有者和管理者不能签发模块，也不能安装未签名的模块。

## 15. 仍待确认

1. 管理者的范围粒度：按「全部服务」一档，还是可以细到「只管某几个服务」。建议第一阶段只做一档。
2. 任务有效期默认 24 小时、尝试上限默认 3 次，是否符合预期。
